# Hochzeitslocation

Swiss wedding-venue listing site: one listing page with filters, one detail page per venue, and a Merkliste without login. It is modelled on eventlokale.ch's wedding search. Scope, settled decisions, requirements and the cycle order live in `docs/rpi-cycles.md`; read it before starting a cycle.

## Tech Stack

- Symfony 7.4 (LTS) on PHP 8.5, served by php-fpm behind nginx
- PostgreSQL 18 with `pg_trgm`, `unaccent`, `cube` and `earthdistance` (Neon in prod, same major locally and in CI)
- Doctrine ORM 3 / DBAL 4, hand-written SQL migrations
- Symfony Messenger with one synchronous `command.bus`
- Twig, Forms, AssetMapper; no Node, no JS framework (S1, S3)
- Docker Compose for everything local: `php`, `nginx`, `database`, `mailpit`

## Architecture

Module-first modular monolith: `src/<Module>/<Layer>/`, namespace `App\<Module>\<Layer>`.

- Modules: `Geo`, `Media`, `Venues`, `Search`, `Favorites`, `Inquiries`, `Seo`, the back office's `Admin`, `Cms`, `Crm`, plus `Shared` for building blocks.
- Layers inside a module: `Controller`, `Command` (command DTOs), `CommandHandler`, `Entity`, `Repository`, `ReadModel` (DBAL queries returning `final readonly` view objects), `ValueObject`, `Exception`, `Form`, `Console` (console commands), `Twig` (Twig filters and functions), `Mailer` (a module's emails), `EventListener`, `Event` (a module's published events), `Extension` (back-office extension points and their implementations), `Security` (security user, provider, authenticators), `Messenger` (bus middleware).
- Allowed module dependencies (everything may use `Shared`; `Shared` uses no module):

  | Module | May depend on |
  |---|---|
  | Geo | — |
  | Media | — |
  | Venues | Geo, Media |
  | Search | Venues, Geo, Media |
  | Favorites | Search, Venues |
  | Inquiries | Venues |
  | Seo | Search, Venues, Geo |
  | Admin | — |
  | Cms | Admin, Venues, Geo, Media |
  | Crm | Admin, Venues, Geo, Inquiries |

  No public module depends on `Admin`, `Cms` or `Crm`.

- Reads: public pages go controller → `ReadModel` (DBAL, `final readonly` view objects), never entities. Writes: controller or console command → command → `command.bus` → handler. There is no query bus.
- phpat enforces layers, modifiers and module boundaries during `make phpstan` (rules in `tests/Architecture/`). Details: `.claude/rules/php-architecture.md`, `.claude/rules/cqrs.md`, `.claude/rules/read-model.md`.

## Validation strategy

Three layers, each catching what the previous one cannot:

1. **Forms** validate input shape (Symfony Form + Validator on a form data class).
2. **Handlers** enforce business rules and throw `DomainException` subclasses.
3. **Database constraints** guarantee uniqueness and integrity under concurrency.

Details: `.claude/rules/validation.md`.

Shared holds the contracts and the read side, so a public module declares and renders a block without naming Cms; reading `content_blocks` in `Shared\ReadModel` is SQL, not a PHP dependency on Cms (phpat sees no module edge).

- **Contracts** (`Shared\Extension`, autoconfigured): `ContentBlockDefinition` (tag `content_block.definition`; `key()` dotted lower-case and never `landing.…`, `label()`, `placement()`, `maxLength()` in code points of the trimmed text, `fallback(): ?TranslatableInterface`), collected by `ContentBlockRegistry` (`all()` sorted by key, `get()`; a duplicate key throws `\LogicException`). `FooterNoteBlock` (`KEY` `footer.note`, 300, no fallback, strings `shared` `blocks.footer_note.{label,placement}`). `LandingPageSource` (`pages(): list<LandingPageEntry>`, `page(string $keyPrefix): ?LandingPageEntry`) is implemented by Seo. `Shared\ValueObject\LandingPageEntry` (`keyPrefix`, `type`, `name`, `venueCount`, `passesThreshold`, `url` absolute and only above the threshold, `defaultIntro`, `defaultTitle`, `defaultDescription`; `FIELDS` `intro|title|description`, `blockKey($field)` → `landing.canton.zh.title`).
- **Reader:** `Shared\ReadModel\ContentBlocks` (`kernel.reset`) keeps the whole table as one item `snapshot` (`ContentBlocks::ITEM`, locale → key → Markdown) in pool `cache.content_blocks` (`cache.app`, no expiry). `text()`/`html()` fill a cold pool; `peek()`/`peekHtml()` read the pool only and never query; `refresh()` rebuilds it (Cms, after a save's commit); a cache error never fails a page. Every write to the pool is under the transaction-level advisory lock `ContentBlocks::LOCK`, taken before the SELECT: `refresh()` waits for it, a cold read tries it and, when it is taken, serves what it read and stores nothing, so an older snapshot cannot replace a newer one. A cold fill therefore costs a transaction, the try-lock and the SELECT. The item never expires, because a page that only peeks must keep the note and a cached listing may be all that would warm an empty pool; instead the item carries its build time, and `text()` rebuilds a snapshot older than `ContentBlocks::MAX_AGE_SECONDS` (a day, `Psr\Clock\ClockInterface`) while `peek()` keeps serving it, and any other item shape is a miss. That caps what no lock covers: a refresh that failed or died after the commit, a restore, a direct SQL change. The cap is about two days with #19's TTLs (read from them, not run): `text()` runs only on a PHP render and listings stay cached until Zurich midnight, so a snapshot built just after midnight survives another cached day. `make sf c="cache:pool:clear cache.content_blocks"`, then `make sf c="app:http-cache:clear"` (the page store still holds the old text) and a hit on the plain listing apply such a change at once: `cache:clear` leaves this pool alone, because `cache.app` lives in `var/share/<env>/pools/app`. HTML comes from `MarkdownRenderer`, memoized per request; `render()` maps `<h1>` to `<h2>` (the page has its one h1; `MarkdownRenderer` stays as it is for the rest of the back office) and a body with no visible text (a lone link reference, only NBSP) counts as no block. No cross-locale fallback: a locale without a row gives null and the page shows its own catalogue text.
- **Twig** (`Shared\Twig\ContentBlockExtension`, the main request's locale): `content_block(key, fallback = null)` (safe HTML, else the escaped fallback in a `<p>`, else `''`; the fallback is the caller's, else the `ContentBlockDefinition`'s through `ContentBlockRegistry`; may query once on a cold pool), `content_block_peek(key)` (pool only: the footer, error pages), `content_text(key)` (the raw text, else the definition's fallback, for a value that is not Markdown; no template uses it yet). Capture it as `{% set x %}{{ content_block(…) }}{% endset %}`: a plain `{% set x = … %}` loses `is_safe` and `{{ x }}` escapes the HTML, while the captured set is `Markup` (`''` when empty) and survives a `with_context = false` include. Never `|raw`.
- **Footer note:** `templates/shared/_footer_note.html.twig` fills the slot after #18's `_footer_links` in `layout/_footer.html.twig` (`.site-footer__note`, `assets/styles/layout/_footer.scss`) through `content_block_peek()` only, so error pages stay query-free (`ErrorPagesQueryFreeTest`, warm and cold). Cold-pool window: while the pool is empty (a fresh `var/share`, `cache:pool:clear`) a page that only peeks lacks the note until a listing or landing hit warms the snapshot; age alone never empties it. A filtered or page-2 listing reads no block, so it warms nothing, and neither does a listing answered from the page store (#19). A page rendered in that window stays in the store without the note for up to its `s-maxage` (a day), until the next purge or clear, so #20 keeps `var/share/<env>/pools` across a deploy or hits a listing before the first public page. A CMS save never leaves the pool cold, and its purge reaches every page, the footer note on detail and legal pages included.
- **Tests:** `tests/Support/Cms/ResetsContentBlocks.php` (`resetContentBlocks()`: the pool is a filesystem pool shared by every test, and a save inside a rolled-back test transaction stores rows that vanish, so call it after the kernel boots and in `tearDown()`), `tests/Support/Cms/HoldsAdvisoryLocks.php` (a second session, because the test's own connection may retake its lock; the test's transaction keeps a lock until the rollback, so take the second session's lock before the first save or refresh), `tests/Support/Cms/RecordingCachePool.php` (`saves`, `onSave`: only record in the callback, because `rebuild()` swallows whatever a save throws, a failed assertion too), `tests/Integration/Shared/ContentBlocksTest.php` (`outsideTheTestTransaction()` runs `rebuild()` on a real BEGIN and COMMIT, the only way to pin that the save comes before the lock's release), `tests/Unit/Shared/Extension/ContentBlockRegistryTest.php`, `tests/Unit/Shared/Twig/ContentBlockExtensionTest.php`.

Built in #19 (`performance-caching`). No migration, no package. This supersedes every `s-maxage=600` line in this file.

- **HttpCache in prod only:** `when@prod` `framework.http_cache` (`trace_level: short`, `X-Symfony-Cache`, `default_ttl: 0`, no client reload or revalidate), with no `public/index.php` change; dev and test stay uncached, so a test wires it by hand (`Tests\Support\Http\ThroughHttpCache`). The short trace reads `miss/store`, then `fresh`. The store is `%kernel.share_dir%/http_cache`, `var/share/<env>/http_cache` under `APP_SHARE_DIR=var/share` (`.env`, Symfony's recipe), so `cache:clear` does not empty it; only `app:http-cache:clear` does. **Nothing but the web user may write the store** (#20: no console run, cron or deploy step as another user leaves a file there). Three failure modes: `var/share/<env>` not writable is a 500 on every URL, `/health` included (`Store`'s constructor cannot create the directory); a store that exists but is not writable answers a new URL `miss/store-failed` and **any URL with a stale entry a 500**, because `Store::lock()` calls `flock()` on a failed `fopen()` (`Store.php:87-88`; fixing it means replacing the `Store`, handed to #20 with its permission check); and the clear race below.
- **`Shared\Http\PublicCache`** holds every lifetime and every new public route uses it: `page()` (a day, `stale-while-revalidate` and `stale-if-error` a day), `listing($now)` (the same, `s-maxage` until the next Zurich midnight, because a listing's order uses the day's seed and page 1 and page 2 must share one), `MISSING_TTL` 3600 (a thrown 404 or 410, through `#[Cache]`, which takes only constants and never overwrites a directive the controller set), `COUNT_BROWSER_TTL` 60, `PLACES_BROWSER_TTL` 3600 (`_search_places`: browser an hour, `s-maxage` `PAGE_TTL`). No browser `max-age` on HTML, so a purge reaches a visitor on the next navigation. `health` is `no-store, private`.
- **`Shared\Http\HttpCacheClearer`** has two ways to discard the store (`invalidate()` makes every entry miss, `clear()` empties it), and never throws (it runs after a committed change; it logs class, file and line, never the message). `invalidate()` is the purge: it renames only the metadata (`md/`) away and removes it, so every URL misses at once, and a request between `Store::lookup()` and the body read still finds its body (bodies in `en/` are content-addressed and never rewritten, so one cannot outlive its metadata as a stale page). A purge therefore frees no disk. `clear(): bool` renames and removes the whole store and any `.purged-*` leftover; it is the only call that frees disk, and a request that looked up a body just before it answers Symfony's raw 500 page (no SEC-1 headers): about 1–3.5×10⁻⁴ per clear per request/s (at 1 request/s, one 500 in about 3,000–9,000 clears) (`docs/performance-baseline.md` §5). The purge path measured 0 in 1,063 clears at 403 request/s. `usage()` walks bytes and files, leftovers included.
- **`app:http-cache:clear [--if-over-limit]`** (`Shared\Console\ClearHttpCacheCommand`) calls `clear()` directly with no bus, because `command.bus`'s `doctrine_transaction` would wake Neon for a file operation, so it runs in the deployed app directory as the web user (#20). A failed clear prints an error and exits 1, because #20's cron sees only the exit code. #20 runs it nightly at 00:05 and after `app:geo:import-towns` and `app:media:regenerate`, and `--if-over-limit` on a 5-minute cron. **The size guard is the only bound on the store:** `Store` never evicts and every filter state, `?q=` value and unknown slug is a new key (an anonymous client measured 20 MiB/s on two local cores). `--if-over-limit` walks the store once and clears it above `HTTP_CACHE_MAX_BYTES` (5 GiB) or `HTTP_CACHE_MAX_FILES` (1,000,000; small pages use up inodes before bytes), both from `.env`; within both limits it prints nothing, because cron mails any output. The store can overshoot a limit by about one cron interval of write rate (measured scaled down: limit plus 0.73 of an interval; at the local worst rate of 25 MiB/s and 5 minutes, about 7.5 GiB over), so production's quota must leave that room. The byte limit counts file bytes, not disk blocks; small entries (404s, counts) take about 6 times their size on disk, and for them the file limit is the bound. The walk takes about 4–9 µs per file (`docs/performance-baseline.md` §9). The guard bounds only the store: anything else can still fill the disk, and a limiter whose pool cannot save its count fails open on a full disk (measured for `phone_reveal`: 25 of 25 allowed against 20; `inquiry_submit` and the admin login share the storage).
- **Accepted windows:** a render in flight during a save can store the old page after the purge, and that URL stays stale until the next `clear()`, so until 00:05 at the latest; this bound depends on #20's nightly cron existing. A clear also removes the `stale-if-error` fallback for every page not rendered since.
- **nginx:** `/assets/` `public, max-age=31536000, immutable`, `/media/` `public, max-age=86400`, never `immutable`, because `app:media:regenerate` rewrites the same URLs. A changed `docker/nginx/` needs `docker compose restart nginx`.
- **Client IP:** HttpCache rewrites `REMOTE_ADDR` and forwards the visitor, so limiters stay per visitor and `isSecure()` holds with no `trusted_proxies` value (`ClientIpBehindHttpCacheTest`). A proxy in front is #20's. A no-JS Merkliste POST invalidates the page in its `Location`, one page and harmless.
- **Accepted trade (D4):** a cached detail page shares one fill-time token, which has no maximum age, so the bot rule weakens to "at least 3 s since that page was rendered".
- **Guard:** `PublicPagesStartNoSessionTest` walks every route outside `/admin`, with every declared method and real parameters, and `PublicCacheHeadersTest` pins the exact `Cache-Control` per route and answer. A new public route needs parameters in the walker (`$parameters`), a row in the table, and, if it is not `public` with an `s-maxage`, `PRIVATE_ROUTES`; only `COOKIE_ROUTES` (`merkliste`, `merkliste_toggle`, `merkliste_sync`) may send a cookie. `Session::isStarted()` proves nothing after the response, because the listener saves and closes the session: check `getUsageIndex()`. Fixtures: `Tests\Support\Http\PublicRouteFixtures`.

### Geo

Cantons, towns, postcode/town lookup, distances.

Built in #3:

- Tables: `cantons` (26 rows seeded by the migration; primary key `code`, the lower-case canton code — a documented exception to `EntityId`, since it is a code-keyed vocabulary row; `bfs_number`, `slug`, `svg_id`, centroid), `towns` (UUID `id`; one row per `(canton_code, name)`, lowest ZIP, `slug`, `bfs_number`, `lat`/`lng`, municipal `population`) and `town_zips` (every ZIP of a town). Entities in `Geo\Entity`; FK targets for later modules are `towns.id` and `cantons.code`.
- SQL functions `geo_fold(text)`, `geo_fold_de(text)` (ü → ue) and `geo_search_key(text)` (both folds). New SQL that compares place names must fold through them so it matches the GIN trigram index `idx_towns_search_key` on `geo_search_key(name)`. The GiST index `idx_towns_earth` on `ll_to_earth(lat, lng)` serves radius queries. Both are expression indexes, invisible to DBAL and deliberately unmapped.
- `app:geo:import-towns [path]`: idempotent import of `data/geo/towns.csv` (console → `ImportTowns` → handler → `TownRepository` upserts). Never deletes towns, only stale ZIP rows; reports stale towns. Run by `make seed` and once after each deploy's migrations.
- Read models: `PlaceLookup::suggest(string $q): list<PlaceSuggestion>` (cantons, then towns; ZIP prefix, name prefix, word prefix, trigram; by population; ≤ 8) and `TownLocator::withinKm(string $townId, float $km): list<TownDistance>` (0 < km ≤ 200, nearest first, centre town included).
- Labels: the `Canton` enum (`Geo\ValueObject`, implements `TranslatableInterface`) and the `geo` domain (`translations/geo+intl-icu.de.yaml`, keys `canton.<code>`). Canton suggestions carry only the code.
- Map: `{{ canton_map() }}` inlines `assets/maps/cantons.svg` (`<g id="cantons">` with `<path id="ch-<code>">`, `<g id="lakes">`); source, licence and build recipe in `assets/maps/LICENSES.md`. Dataset source note: `data/geo/SOURCE.md`.

Built in #10 (`filter-region`):

- `Geo\ReadModel\PlaceResolver::resolve(string $place): ?ResolvedPlace` (town UUID or 4-digit ZIP; a ZIP means its most populous town, the rule of `ListingSql`; memoized per value, misses too, `kernel.reset`). `ResolvedPlace`: `name`, `zip`, `lat`, `lng`, `label()` ("8712 Stäfa").
- `PlaceSuggestion` has `lat`/`lng` (null for a canton), so town entries of `/_search/places` now end in `"lat", "lng"`. A map pin uses the affine fit in `assets/js/region-filter.js` (2.29 SVG units per km, 96.4 % of towns land in their own canton).

### Media

**Built in #5 (`venue-media`).** Media depends on nothing but Shared; it knows paths and pixels, never venues.

### Favorites

Merkliste cookie codec, toggle endpoint, `/merkliste` page.

**Built in #13 (`merkliste`).** No migration, no table: the list lives in the browser. Composer `symfony/security-csrf` (shared with #14).

- **Cookie:** name `merkliste`, host-only, `Path=/`, venue numbers in saved order, comma-separated. On the wire the comma is percent-encoded (`12%2C34%2C56`) on both sides; both readers also accept a raw comma. `Max-Age` 34560000 (400 days, renewed on every write), `SameSite=Lax`, `Secure` on HTTPS, not `HttpOnly` (JS reads it). An empty list deletes it. A trailing comma (`12%2C34%2C`) marks a list written by JS and not yet re-issued: only JS writes it, both readers ignore it, and `POST /merkliste` and `GET /merkliste` drop it.
- **Codec:** `Favorites\ValueObject\MerklisteCookie` (`NAME`, `MAX` = 100, `MAX_AGE_SECONDS`): `fromRequest()`, `parse()`, `isValidNumber()`, `numbers()`, `has()`, `isFull()`, `toggled()`, `without()`, `only()`, `value()`, `toCookie()`. A token matches `^[1-9]\d{0,9}$` and is ≤ 2147483647, so a crafted value cannot reach Postgres out of range; garbage is dropped, duplicates keep their first position, the first 100 win. At 100 an add is refused, nothing is evicted; the codec owns that rule because no server-side list exists (`.claude/rules/validation.md`'s example assumes one). `assets/js/merkliste.js` repeats the rule and the format; change them together.
- **Toggle:** `merkliste_toggle` `POST /merkliste/{number}` (`MerklisteToggleController`), the no-JS path. No command or handler (`.claude/rules/cqrs.md`): nothing is persisted, and a handler cannot set a response cookie. No database either, stale numbers are `/merkliste`'s job. CSRF comes first, through the stateless `SameOriginCsrfTokenManager` (token id `submit`, field `_token`, constant value `csrf-token`, so cached HTML is the same for everyone); a failed check answers 403 and no cookie. This is required: `SameSite=Lax` keeps the cookie off a cross-site POST, but the answer's `Set-Cookie` would still be stored and replace the whole list. Then a 303 to the same-origin `Referer`, else `/merkliste`; a refused add at 100 goes to `/merkliste` with no cookie. `intent=remove` (the exact string, sent by `_remove_button`) only ever removes through `without()`: the same removal twice leaves the entry gone, an absent number sends no `Set-Cookie`, and it is never refused at 100. Without it the route is a true toggle, because the Merken button on a cached page cannot know the state. A number above the INTEGER range is 404. All answers are `private, no-store`, `X-Robots-Tag: noindex, nofollow`.
- **Sync:** `merkliste_sync` `POST /merkliste` (`MerklisteSyncController`) makes the server the last writer, because WebKit caps a cookie written by `document.cookie` at 7 days and leaves one set by a response alone (MK-2). It has no number, so it cannot flip anything, and it echoes the list from the request's `Cookie` header: an empty list writes nothing and never deletes, a clean list writes nothing, anything else is re-issued normalised, which drops the marker. Same CSRF check as the toggle. It answers 204 with no `Location`, so `HttpCache` invalidates no cached page. No database, no session. `merkliste.js` calls it 3 s after the last write of a burst (plain `fetch`, 2 s timeout), 3 s after a page load or bfcache restore that finds the marker, and at once with `keepalive` when the tab is hidden or on `pagehide`. No marker, no request: a visitor with no list or a clean one never sends it, nor does a marked value with no valid entry, and `focus` and `render()` never do. A failure stays silent, the marker stays, and the next page view retries. An answer that leaves the marker (a proxy dropped `Set-Cookie`) is not retried until this tab writes again, so a page cannot loop. Because the server cannot see the browser's cookie, a landing can overwrite a newer write, so each tab keeps a journal of its writes until a sync has landed and, one delay later, nothing of its own is left to send (the cookie is clean, or it carries another tab's marker), or until the page is left (its keepalive carries the list, and whatever runs meanwhile is newer): it re-asserts additions before every sync and at every landing, and removals only at its own landing and only when they came after that flight's snapshot. `MerklisteScriptTest` pins `SYNC_TIMEOUT_MS + 1000 <= SYNC_DELAY_MS`, which that rule needs across tabs.
- **Page:** `merkliste` `GET /merkliste` (`MerklisteController`), the only GET that reads the cookie. Cards come from `ListingQuery::cardsByNumbers()` in saved order through `search/_card.html.twig` with `action: 'remove'`. It prunes: when the normalised list (garbage, duplicates, unpublished or deleted venues gone) differs from what it received, it sends a `Set-Cookie`, so a venue unpublished for a while leaves a list if the page is opened in that window. `private, no-store`, `noindex, nofollow` in the header and the `<meta>`. The empty state, count and full notice are always rendered, `hidden` when not needed, so JS can reveal them.
- **Cached pages never read the cookie:** no `Set-Cookie`, no `Vary: Cookie`, byte-identical HTML. `MerklisteCookieDoesNotVaryTest` pins this with a frozen clock (`mockTime()`), so time-dependent page content cannot flake it.
- **`assets/js/merkliste.js`** loads on every page from `base.html.twig` (one recorded line beside `overlay.js`, because the header count needs it and `{% block scripts %}` is overridden per page). It reads the cookie, sets `aria-pressed` on every `[data-merken]`, fills `[data-merkliste-count]` and the heart's `aria-label`, and refreshes on bfcache restore, when a tab becomes visible and on `window` `focus` (`visibilitychange` does not fire for two side-by-side windows); on `/merkliste` a refresh reloads when the cookie's list differs from the rendered cards, and it never runs at load, so it cannot loop. - **One guest action, one row (double submit):** the rule is server-side, because the form has no JS and PHP finishes a POST the browser cancelled (nginx 499). `SubmitInquiry` computes `ValueObject\InquiryFingerprint` (HMAC-SHA-256 with `kernel.secret` over the venue id and the normalised payload: NFC, collapsed whitespace, lower-case e-mail; a corrected typo is a new inquiry), takes `pg_advisory_xact_lock` on it, and returns the newest row with that fingerprint from the last 10 minutes as `SubmittedInquiry(id, isRepeat: true)` whatever its mail status, else inserts. `DeliverInquiry` then claims the row (`InquiryRepository::claim()`: `SELECT … FOR UPDATE`, held until commit, across both SMTP calls), so a repeat waits for a delivery in progress and answers with its real outcome. `sent` sends nothing and gives the same 303; `failed` delivers again; `pending` with the claim free means the earlier delivery ended without a result, so it delivers too. `InquirySubmitted` is published for a new row only. The duplicate still costs one `inquiry_submit` token. Use transaction-level advisory locks only: `persistent: true` and any pooler would keep a session-level one. The fingerprint is not a person key: keyed, per venue, over the whole payload, and purged with the row. #29 must not copy it.

## Exception conventions

- Every business error is a `final` class in `<Module>\Exception` extending `App\Shared\Exception\DomainException`.
- Create them through named constructors (`VenueNotFound::forSlug($slug)`), not `new` with a message at the call site.
- Infrastructure errors (DB down, HTTP failures) are not domain exceptions; let them bubble.

## Database & migrations

Hand-written SQL migrations only; never `doctrine:migrations:diff`. Every migration has a `down()`. Name each migration `VersionYYYYMMDDHHMMSS` from the wall clock at the moment it is written; the Schema ownership column of the overview in `docs/rpi-cycles.md` decides which cycle may alter a table. Naming, types and entity mapping rules: `.claude/rules/database.md`.

## Local ports and parallel lanes

Host ports default to 8080 (nginx), 5432 (Postgres) and 8025 (Mailpit), the main checkout's lane. Each cycle runs in its own git worktree, and each worktree is its own Compose project (own containers, volume and `app_test`). Set the lane's ports per shell:

```sh
export NGINX_HOST_PORT=8081 DB_HOST_PORT=5433 MAILPIT_HOST_PORT=8026
```

or in a git-ignored `compose.override.yaml`. The lane table is in `docs/rpi-cycles.md` §Running cycles in parallel.

## CI

`.github/workflows/ci.yaml` starts the same Compose `php` + `database` services and runs `make vendor`, `make lint`, `make test`. `make lint` passing locally means CI lint passes. Pre-commit (`.pre-commit-config.yaml`) runs `make cs-fix` and `make phpstan`; activate with `brew install pre-commit && pre-commit install`.

## Order of work

`make cs-fix` → `make lint` → `make test`. Every UI cycle also runs the checks in S11 of `docs/rpi-cycles.md`. See `.claude/rules/code-quality.md`.
