### Inquiries

Inquiry form on the venue detail page, `inquiries` table, both mails, retention, `InquirySubmitted`. Read it by hand before touching the POST flow, a mail or code that reads `inquiries`.

## Data and POST flow

- **`inquiries`** (baseline migration): `venue_id` is `ON DELETE SET NULL`, so rows outlive venues; `venue_number`, `venue_name`, `venue_slug`, `recipient_email` (always the venue's address) are snapshots; `delivered_to` is the real recipient (differs under the override); outcomes are `MailStatus` (`pending|sent|failed|skipped`); the Anlass is `Occasion` (`occasion.<code>`). No IP or user agent is stored. `InquiryVocabularyChecksTest` pins the CHECK lists. The CRM never alters the table.
- **Route** `inquiry_submit` `POST /eventlokal/{slug}/anfrage`: 404 unknown or no address, 410 unpublished, history slug accepted. Checks in order: honeypot `website` (303, nothing stored), form (422), `FillTimeToken` (at least 3 s, no maximum age: pages are cached), limiter `inquiry_submit` (5 per hour per IP, 429 + `Retry-After`, only valid posts count). A failed venue mail answers 503 with the G7 «gespeichert» state (see Qualification). All responses `private, no-store`, `X-Robots-Tag: noindex, nofollow`, no cookie.
- **Double submit = one row**, server-side (no JS; PHP finishes cancelled POSTs): `SubmitInquiry` locks the `InquiryFingerprint` (HMAC of venue + normalised payload) with `pg_advisory_xact_lock` (transaction level only: `persistent: true` or a pooler would keep a session lock) and returns the newest row of the last 10 minutes as `SubmittedInquiry(isRepeat: true)`. `DeliverInquiry` claims the row (`FOR UPDATE` until commit, across both SMTP calls), so a repeat waits and gets the real outcome: `sent` sends nothing, `failed` and `pending` deliver again. A repeat is not published but costs a limiter token. The fingerprint is no person key: the CRM must not copy it.
- **Delivery** (own command: the row is committed before any SMTP call): venue mail, then the guest copy only if it went out. The venue mail catches `TransportExceptionInterface|RfcComplianceException|HandlerFailedException` (`Mailer::send()` unwraps only transport errors); anything else bubbles out of the handler, row `pending`, and the controller answers it like a failed mail (G7). The guest copy catches `\Throwable`: nothing may undo the record. A `sent` row is never mailed again, nor its `failed` copy. Gap: a crash between SMTP acknowledgement and commit re-mails the venue. `SubmitInquiry` refuses unpublished or address-less venues, guests outside 1-5000, past dates (Europe/Zurich).
- **CSRF** is stateless (`csrf.yaml`): `_token` is the constant `csrf-token`; the check is `Sec-Fetch-Site`, else `Origin`/`Referer` (none: refused), so the form fits a cached page. Tests send `HTTP_SEC_FETCH_SITE: same-origin`.

## Form, copy, mail

- `{{ inquiry_form(venue, form = null, undelivered = false) }}` fills the detail page's `{% block inquiry %}`: nothing without an inquiry address, `_undelivered.html.twig` when the POST passes `undelivered` (G7), the confirmation on a signed `?anfrage=gesendet`, else the form; same HTML for everyone (S10). `#anfrage` is appended after `UriSigner::sign()`, which hashes fragments. `InquiryFormFactory::create(VenueDetail)` alone builds the form.
- **E-mail rule** (`InquiryData`): strict `Email`, then `EMAIL_SHAPE` (ASCII local part, no Unicode separator or control character, an IDN domain stays valid). The form may refuse more than `chk_inquiries_email`, never less (`InquiryEmailRuleTest`); Postgres' `\s` is Unicode-aware, PCRE's without `/u` is not, so never copy a CHECK regex into PHP untested on both.
- **Copy** is "du" (`PublicCopyAddressTest`): the guest copy greets "Danke, {name}!", the venue mail opens "Neue Anfrage für {venue}". Constraint messages: `validators` (`inquiry.<field>.<rule>`); the rest: `inquiries`.
- **Mail** (`InquiryMailer`): From `MAILER_FROM`; Reply-To is the guest (venue mail) or `%site.contact_email%` (guest copy). The context has no `email` key (`TemplatedEmail` reserves it, the renderer throws): the guest's address is `guest_email`. `INQUIRY_RECIPIENT_OVERRIDE` redirects the venue mail (original in `X-Inquiry-Original-Recipient`), never the guest copy, and all CRM mail; production must leave it empty (`ProductionRecipientOverrideTest`). Log lines put every value in a placeholder (the default `Logger` drops the rest of the context), never an exception message (it can quote an address).

## Event and retention

- **`InquirySubmitted`** (`inquiryId`): published by `InquiryEvents` from the controller after both commits, once per stored row, also on a failed venue mail; repeats and honeypot hits publish nothing. The outcome can change later: read `inquiries`, keep no copy. `InquiryEvents` catches `\Throwable` per dispatch and logs, so a subscriber cannot fail the guest; a throwing one stops the later subscribers, so each (CRM, Stats) catches its own.
- **Retention (LEG-2):** `app:inquiries:purge [--dry-run]`, `%inquiries.retention_months%` = 12 (in `/datenschutz`), `bin/cron-daily` step `inquiries-purge`. No purge event: `crm_inquiry_links` cascades and the CRM's `inquiry` entry holds no personal data, so the CRM must not copy any. `app:inquiries:report-stuck [--minutes=15]` is the hourly staff alert since G7 (see Qualification), no longer a `cron-daily` step.
- **Funnel (G8):** `DeliverInquiryHandler` (fifth constructor argument `MessageBusInterface`) records `inquiry_delivered` (`Shared\Command\RecordFunnelEvent` with the venue id or null, `DispatchAfterCurrentBusStamp`) right after `recordVenueMailSent`: once per inquiry (a `sent` row returns before), after the commit, so it cannot undo the record or 5xx the guest, and nothing for a failed venue mail. The row carries no address or name. G7 (`enquiry-quality`) emits it for an unmarked row only, and `MarkInquiry` withdraws or re-records it (see Qualification). Tests: `tests/Application/Inquiries/SubmitInquiryFunnelTest`, the assertion in `SubmitInquiryDeliveryFailureTest`.

## Tests

- `InquiryFormFields::valid()` posts a back-dated fill-time token. `MailerInterface` is inlined in the test container: hand-build `InquiryMailer` with `RecordingMailer`. `SmtpSink` is a real SMTP server without SMTPUTF8 (Mailpit has it). `SubmitInquiryConcurrencyTest` forces the overlap of two POSTs with `pg_locks`. Each mail logs two mailer events: use `assertEmailCount()` or filter `!isQueued()`. A dead SMTP needs `MAILER_DSN` set before `createClient()`.

## Event fields (F9 `inquiry-event`)

- **Columns** (migration `Version20261107173925`): `event_type` (NOT NULL, a `suitable_for` code; no FK, CHECK on the code shape), `company`, `date_flexible` (CHECK: `event_date` or `date_flexible`), `start_time` (`TIME(0)`, the command carries `H:i`), `catering_wish` (`in_house` | `external_allowed` | NULL), `budget_chf` (1 to 1,000,000). `occasion` and the `Occasion` enum are gone.
- **Vocabulary:** `ReadModel\InquiryVocabularyQuery` (`eventTypes()`, `cateringWishes()`, `Term` labels, `kernel.reset`) is the only list of choices, for the form and the handler; `InquiryVocabularyQuery::CATERING_WISHES` is pinned to the CHECK by `InquiryVocabularyChecksTest`. A new event type is a F3-style term row, no change here.
- **Handler rules** (after the existing ones): unknown event type or catering code `UnknownInquiryTerm`, neither date nor "flexibel" `EventDateMissing`, budget out of range `BudgetOutOfRange`. `InquiryFingerprint` covers every new field.
- **Mails:** both render `email/_facts.html.twig` (`facts(i)` macro: Anlass, Gäste, Wunschtermin with "(flexibel)", then Beginn, Catering-Wunsch, Budget, Name, Firma, E-Mail, Telefon; optional rows only when given). The venue subject names name, event type, date and guests. `InquiryMailer::context()` keys are snake_case (`event_type`, `date_flexible`, `start_time`, `catering_wish`, `budget_chf`, `company`).
- **Not asked:** the room layout (D4; follow-up if the PO wants it).

## Qualification (G7 `enquiry-quality`, D19, D56)

- **Columns** (migration `Version20261108180917`): `qualification` (`qualified` | `unqualified` | NULL before the first delivery), `qualification_reason` (`not_delivered`, `duplicate`, `event_type_not_offered`, `guests_outside_capacity`, `date_too_far`; set exactly when unqualified, `chk_inquiries_qualification_reason_pair`), `qualification_override` (`spam` | `test` | NULL), `stuck_alerted_at`. Enums `ValueObject\{Qualification, QualificationReason, InquiryOverride}`, pinned by `InquiryVocabularyChecksTest`. The backfill made `sent` rows `qualified` and every other row `unqualified`/`not_delivered`.
- **Rule:** `ValueObject\QualificationRule::evaluate(QualificationFacts)` is pure; the first failing reason wins in the order above. Constants (one line each): `DUPLICATE_WINDOW_DAYS = 30` (same venue, same `lower(email)`, an earlier `sent` unmarked row), `DATE_HORIZON_MONTHS = 24` (from the Zurich creation day), `ZONE`. `event_type_not_offered` only when the venue lists at least one `suitable_for` term; the guest fit is F5b's `Venues\VenueCapacity::guestsFitSql()` (venue range or any room range). Not criteria: catering, budget, disposable domains, phone.
- **When:** `DeliverInquiryHandler` reads `ReadModel\QualificationFactsQuery` (one DBAL statement) **before** the venue mail, so nothing after the mail can fail, and stores `recordQualification()` on both branches. It is a snapshot of each delivery: a resend recomputes it. A gone venue passes the venue criteria.
- **Staff mark:** `Command\MarkInquiry(inquiryId, ?InquiryOverride)` is audited (summary `{override}`); `MarkInquiryHandler` throws `Exception\InquiryNotFound`. On a delivered row, marking withdraws its `inquiry_delivered` step (`WithdrawFunnelEvent` at `venue_mail_sent_at`, the nearest row within an hour), unmarking re-records one at the unmark time; spam ↔ test touches nothing. A marked row resent records no step.
- **Counted qualified:** `ReadModel\QualifiedInquirySql::where($alias)` (qualified and unmarked) is the one predicate; Stats reads it for the scorecard, G10's owner report is to read it too.
- **Hourly staff alert:** `app:inquiries:report-stuck [--minutes=15]` (`bin/cron-hourly`, `40 * * * *`) dispatches `AlertStuckInquiries`; `ReadModel\StuckInquiries::due()` lists `failed` rows, and `pending` rows past the cut-off, created in the last `WINDOW_DAYS = 7` days, unmarked, never alerted (at most 50, oldest first). `InquiryMailer::sendStuckAlert()` mails `%site.contact_email%` (`inquiries/email/stuck_alert.html.twig`, copy under `email.stuck`; venue name and number, state, Zurich time, CRM link; no guest data). Only after the mail went out does the handler set `stuck_alerted_at`, so each inquiry is mailed once and a second run writes and sends nothing; a failed mail writes nothing, the command prints the ids and `Mail to staff failed: …` (exit 0) and the next hour retries. A failed resend is not alerted again.
- **Guest state:** a venue mail that did not go out, or any unexpected error in `DeliverInquiry` (logged with placeholders only), answers 503 with `templates/inquiries/_undelivered.html.twig`: the form heading and the D56 sentence `form.undelivered` (`{name}` = the venue), no form (a resubmit would only duplicate). The row stays `failed` or `pending` for the alert.
- **Tests:** `tests/Unit/Inquiries/{QualificationRuleTest, QualifiedInquirySqlTest}`, `tests/Integration/Inquiries/{QualificationFactsQueryTest, MarkInquiryHandlerTest, StuckInquiriesTest, ReportStuckInquiriesCommandTest, DeliverInquiryHandlerTest}`, `tests/Integration/Migrations/EnquiryQualityMigrationTest`, `tests/Application/Inquiries/{SubmitInquiryDeliveryFailureTest, SubmitInquiryMailErrorTest}`. An unexpected mail error is provoked with a `MessageEvent` listener on `event_dispatcher` (the mailer is inlined).
