### Venues

Venue aggregate (translations, terms, rooms, photos, documents, the Google place ID), detail page, content import, and the write side Cms, Portal and Crm share. Read it by hand before any venue write: **Write side** holds the commands, helpers and invariants, **Content import** the folder path. Venues depends on Geo and Media only; nothing else writes venue tables.

## Data model

Entities in `Venues\Entity` (unidirectional `ManyToOne` only), mapping `orm.mappings.Venues`; schema: baseline migration `Version20261106174839`.

- **Tables:** `venues` is the root; `venue_translations`, `venue_slug_history`, `venue_terms`, `rooms` -> `room_translations`, `venue_documents` -> `venue_document_translations`, `venue_photos` -> `venue_photo_translations` hang off it `ON DELETE CASCADE`; `towns`, `cantons`, `taxonomy_terms` are `RESTRICT`. `venue_photos.width/height/dominant_color/variants` (JSONB, JPEG required) are NOT NULL with CHECKs; unique `(venue_id, room_id, position)` `NULLS NOT DISTINCT` (room NULL = gallery).
- **`venues`:** `number` is an identity column (`GENERATED ALWAYS`, unique): the public number and Merkliste id (S7), not the PK. `tier_id` (NOT NULL, FK to `tiers`, default Free) is the plan; listings order by `tiers.rank_weight` (F12). No `venues.slug`: slug (unique per locale), `summary` (<= 200), `description`, `meta_description` (<= 160), `parking_text` (<= 250) are per locale in `venue_translations`; read with `TranslationJoin::localized('venue_translations', 'venue_id', 'v.id', 't')`. `room_count`, `largest_room_m2`, `max_room_height_m` come from the rooms (`RoomSummary::apply()`), never by hand.
- **Location is optional:** `zip`, `town_id`, `canton_code`, `lat`, `lng` are nullable under `chk_venues_address` (`zip` with `town_id`, `street` needs a town), `chk_venues_coordinates` (both or neither), `chk_venues_town_canton` (a town has a canton; the entity copies it from the town). `venue_translations.region` (<= 60, verbatim) names the place of a venue without a canton. Reads must `LEFT JOIN towns`. `coordinates_from_town` (`chk_venues_coordinates_from_town`) flags town-centre coordinates ("Ortsmitte übernehmen"): not the venue's position, so no map pin, no `geo`; the import always writes it false.
- **Terms:** `taxonomy_terms (term_group, code)`: 10 groups, 118 rows since F3 (`Version20261107140511`; a new row needs a migration), `primary_position` 1-11 for the building chips before "Alle Gebäudearten" (`seminar_room` is chip 3, `wedding_venue` is gone). `TermGroup` = `setting, building, suitable_for, infrastructure, furniture, technology, surroundings, amenity, catering, language`, the order of the CHECK `chk_taxonomy_terms_term_group` and of the keys in `docs/content-format.schema.json` (tests pin both). `suitable_for` holds the 17 event types (`corporate_event, seminar, conference, workshop, meeting, product_presentation, general_assembly, team_event, christmas_party, club_event, apero, birthday, family_celebration, wedding, party, concert, exhibition`; `wedding` is one type among the others, D7); `technology` is the whole event technology (`projector_screen, wifi, sound_system, video_conferencing, stage_lighting, flipchart_moderation, tv_screens, interpreting_system`); `catering` has 12 codes; `amenity` keeps overnight, parking, accessibility and outdoor terms. Labels `term.<group>.<code>` in `venues`. The seven filter groups are `setting` to `surroundings` (without `suitable_for`). `venue_terms (venue_id, term_group, term_code, is_main)` has a composite FK; at most one `is_main` per venue and group (`uk_venue_terms_venue_id_term_group_main`): the main building and setting.
- **Event facts:** `price_level`, `capacity_seated`, `capacity_standing` (1-50000, the owner's numbers, not compared with `capacity_max`; F4 owns them and the room layouts), `instagram` (`https://`), all nullable; `venue_translations.ambience` (<= 60), `capacity_note`, `opening_hours` (<= 250). F3's migration dropped `venues.party/has_curfew/curfew_at` and `venue_translations.party_note`, and made `taxonomy_terms` hold exactly one list (rows that stay keep their `venue_terms`); its `down()` restores the 147 baseline rows and the empty columns (`EventVocabularyMigrationTest` runs both ways on data). Still open after F3: the inquiry `Occasion` is the wedding list (F9).
- **Rooms (F4):** layouts are `Seating` (`seminar, banquet, apero, concert, u_shape, block`), one `rooms.capacity_<layout>_{min,max}` pair each (`Version20261107184701` added U-Form and Block). `Seating::guestRange()`: once a layout states a max, the room's `capacity_max` is the greatest layout max (`chk_rooms_capacity_layouts`) and `capacity_min` the least min of those layouts; `Room` derives it in `offerSeating()` and `reshape()`. Offer the layouts before `reshape()` so a room without layouts keeps its stated range. A new layout = enum case + column pair + range CHECK + a replaced `chk_rooms_capacity_layouts` + `VenueDetailQuery::SEATING_ORDER`.
- **Google:** `google_place_id` (`chk_venues_google_place_id`: `^[A-Za-z0-9_-]{10,255}$`), `google_rating_hidden` (`chk_venues_google_rating_hidden`: only with an ID). The ID is the only Google value we may store (Maps Platform Terms 3.2.3).
- **Import and CMS columns:** `content_key` (unique, kebab CHECK), `content_hash` (SHA-256, only with a key), `cms_edited_at`, `awaits_first_publish`; `rooms.content_key` (unique per venue); `content_imports` (one row per non-dry run: counts, `overwrote_cms_edits`, `venues_cms_edited`, `errors` JSONB); `venue_deleted_content_keys` (tombstone of a deleted content venue).
- **Vocabularies** are enums in `Venues\ValueObject`, labelled in `venues` (`<context>.<value>`, `term.<group>.<code>`); `VocabularyChecksTest` pins each enum on a CHECK column to its `IN` list. `Access` is derived from the distances, never stored: station <= 1 km, highway <= 10, airport <= 30.
- **Entities:** `Venue` has no setters, only intent methods; decimals go in as strings (`'8.4'`). The constructor and `relocate()` take `?Town` and `?Canton`: the town wins. `VenueTranslation::revise()` does not take the event texts: also call `describeEvent()`. `VenuePhoto` throws `RoomOfAnotherVenue` for another venue's room.
- **`VenuePlace`** renders the town, else `Kanton Zürich` (plain `Liechtenstein` for `li`), else the region verbatim (`{{ place|trans }}`).
- **`PhoneNumber::display()`** formats the stored E.164 (`chk_venues_phone`) as `044 123 45 67` or `0800 123 456` (Swiss) or `+423 234 56 78`; anything else stays raw. **`InstagramProfile::fromInput()`** takes a handle, `@handle` or an instagram.com profile URL (also the old `https://@handle` and `https://handle` shapes; handle `[A-Za-z0-9._]{1,30}`) and answers `null` for another site, a post, a reel or another Instagram page: the page, JSON-LD `sameAs` and `venue.md` link the profile or nothing.

## Write side

S8: venues are written only by dispatching `Venues\Command` messages on `command.bus`; slug history, room summaries, the photo pipeline and cache purges live once, in Venues handlers (`<Command>Handler`, in `doctrine_transaction`). Cms, Portal, Crm and consoles only dispatch. Commands are `final readonly`; the audited ones implement `AuditableCommand` (`AuditSubject('venue', (string) $number)`) and their summary names changed fields and short vocabulary values, never free text, contact data, address, region, coordinates or the place ID (`VenueCommandAuditTest`). A new audited command needs its label `history.command.<Command>` in `cms` (listed in `CmsTranslationKeysTest`) and a case in `VenueCommandAuditTest`.

- **Cms cards** carry `venueNumber`, `loadedAt`, `changedFields` and open with `VenueEditing::open()`:
  - `ChangeVenueBasics` (name, slug, tier, capacity range): a rename gives every locale a new slug with history (`VenueSlugs::assign()`), except the default locale's when `newSlug` was typed (`VenueSlugs::change()`); the unique index decides a slug race (`slugTaken`). Portal's `ChangeVenueCapacity` sets the maximum alone and clears a staff minimum above it.
  - `ChangeVenueTexts` (per locale: summary, description, meta description, parking text): keeps the slug; a locale gets a row only with a summary.
  - `RelocateVenue`: "PLZ / Ort" as typed (`TownText::parse()`, "8706 Meilen"; the typed ZIP stays), canton, street, coordinates, three distances (decimal strings), region texts, `useTownCentre`. The town resolves by ZIP and name; the canton select only narrows an ambiguous one (`unknownTown`, `ambiguousTown`); a town needs coordinates; typed or cleared coordinates drop the town-centre flag; the region text is cleared once a town or canton exists.
  - `ChangeVenueTerms` (setting, building, infrastructure, furniture, surroundings plus main building and setting; a group missing from `terms` is emptied, the event groups stay), `ChangeVenueEventFacts` (F3; price level, seated/standing, per locale `ambience`, `capacityNote`, `openingHours` of existing translations via `VenueTranslation::describeEvent()`, the groups `SuitableFor, Catering, Technology, Amenity, Language` since F11, event types checked by `TierLimits` before the first change; `PartyAllowed` is gone), `ChangeVenueContact` (with Instagram), `AnswerVenueFaq` (own catering, daylight; NULL unknown), `ChangeVenueGooglePlace`.
- **Without form state** (`lock()` on the existing venue): `ChangeVenueTier` (nested by the G9 term handlers only, to keep `venues.tier_id` in step; no `cms_edited_at`), `CreateVenue(name, capacityMax)` (always Free) (Cms; Portal nests it with `RelocateVenue`; unpublished, no address, a default-locale translation with an empty summary; returns the number, audited by `RecordVenueCreated` in the same transaction), `PublishVenue` (Cms; Portal nests it in `AcceptSubmission`), `UnpublishVenue` (Cms, Portal; needs nothing, so a venue imported without photos can go offline), `DeleteVenue` (Cms), `AssignVenueGooglePlace` (console).
- **Media** (13; all `lock()`; Cms, and Portal for add, reorder and remove photo): `AddVenuePhoto`, `ReorderVenuePhotos`, `DescribeVenuePhoto` (only listed locales change), `MoveVenuePhotoToRoom`, `RemoveVenuePhoto`, `AddRoom`, `ChangeRoom` (replaces all four seating ranges), `ReorderRooms`, `RemoveRoom`, `AddVenueDocument`, `RetitleVenueDocument`, `ReorderVenueDocuments`, `RemoveVenueDocument`. An unknown locale, seating key or floor value is an `\InvalidArgumentException`: forms and DTOs must restrict them. `RegenerateMedia` is the console's (`app:media:regenerate`).
- **Publish and delete:** `PublishVenue` needs `VenuePublishGaps::missing()` empty: a default-locale summary, a main building and a gallery photo (`room_id IS NULL`); codes `summary`, `main_building`, `photo`, all named at once (`VenueRuleViolation::notPublishable`); an inquiry address is no part of it; Portal's `WizardController` and `SubmitLocationHandler` read the same rule. `DeleteVenue` takes an unpublished venue only (`stillPublished`): cascade, a tombstone for a content venue, `RemoveVenueFiles(wholeVenue: true)` listing only originals no other venue uses.
- **First publish:** `awaits_first_publish` is set only by `CreateVenueHandler` and cleared by every `Venue::publish()`, an import's too. `PublishVenue` answers `true` only for a venue that still had the flag; its dispatcher then calls `Event\VenueEvents::newVenuePublished($venueId)` after the commit (a handler cannot run code after its own): `Cms\Controller\VenueStatusController::publish()`, `Portal\Controller\SubmissionReviewController::accept()`; a new caller must do the same. `VenueEvents` dispatches `Event\NewVenuePublished`, catching and logging a failing subscriber (the Crm), so the publish stands.
- **Funnel (G8):** `PublishVenueHandler` records `venue_published` (`Shared\Command\RecordFunnelEvent` with `DispatchAfterCurrentBusStamp`) on every transition to online: a first publish, a publish of an imported draft and a republish after an unpublish alike; nothing for an already online venue, a refused publish (`VenueRuleViolation`) or a rolled-back surrounding command. Cycles that publish through `PublishVenue` (Portal accept, Cms) must not emit it again; code that calls `Venue::publish()` directly (the content import, `ImportVenueContentHandler`) emits nothing, since an import is no funnel step. `tests/Integration/Venues/PublishVenueFunnelTest`.
- **Errors:** `VenueRuleViolation` (`field`, `translationKey()` = a `cms` key, `parameters`, `missing`; `unwrap(HandlerFailedException)` looks one level deep, so a handler nesting venue commands rethrows the unwrapped rule), `StaleEdit`, `VenueNotFound`, `VenueRowNotFound`, `UnresolvedTown`. A handler checks every rule before its first persist: `doctrine_transaction` rolls back but does not clear the unit of work. An unchanged save is a no-op: no token bump, no `cms_edited_at`, no purge (the audit middleware still writes a row).

### Locking, tokens, helpers

- **`VenueEditing`** is the one way a back-office handler opens and closes a venue (the import never does): `lock($number)` (`SELECT ... FOR UPDATE`), `open($number, $loadedAt)` (`lock()`, then `StaleEdit` when `updated_at` as Unix seconds differs from the form's token; read the token from the database: `updated_at` is `TIMESTAMP(0)`), `close($venue, bool $purgeListings = true, bool $markCmsEdited = true)` (`Venue::markCmsEdited()`, which also moves `updated_at`; after the commit `PurgeVenueCache`, optionally `PurgeListingsCache`). The Google place commands (`ChangeVenueGooglePlace`, and `AssignVenueGooglePlace`, which changes nothing when the venue has an ID) pass `markCmsEdited: false` and `purgeListings: false`: a stamp would freeze the venue against folder imports (the ID is outside the content format), and only the venue's page shows the rating.
- **`RowTokens`:** `close()` bumps `venues.updated_at` on every write, so a venue token would fail an alt save while an upload of the same island commits; `ChangeRoom`, `DescribeVenuePhoto` and `RetitleVenueDocument` check their own row's token (`RowTokens::sql('p.updated_at')` in a read model, `assertFresh()` under `lock()`), reorders compare the whole id list (`Positions::inOrder()`), and the media handlers never call `open()`. A translation mutator (`revise`, `rewrite`, `retitle` on the translation rows) does not move the token: the caller touches the parent (`touch()`, `reshape()`). Read tokens from the database; a test calls `$em->clear()` first.
- **`Positions`:** rows run 1..n per scope (the gallery, `room_id` NULL, whose first photo is the cover; each room; rooms; documents). `renumber()` moves only rows out of place, in two flushes (`POSITION_OFFSET` 10000), because the position uniques are not deferrable; `nextPhoto()`, `nextRoom()`, `nextDocument()` read the database, so flush pending moves first. `VenueRows` queries child rows; a foreign or non-UUID id is `VenueRowNotFound`.
- **Shared rules** (compose, never duplicate): `VenueSlugs` (a venue's own history slugs are free to take back, others' are taken) with `SlugAllocator` (name, `-<town-slug>`, `-2`..., <= 160 chars), `TownResolver`, `RoomSummary`, `VenueTermSet::replace()` (only listed groups change), `RoomFields`, `DocumentTitles` (the default locale always keeps a name or title).

### Media in writes, purges

- **Originals:** uploads are stored `MEDIA_ROOT/cms/<number>/<sha256>.<ext>`, never under the import's `content/<key>/`. `AddVenuePhoto`: `EXTENSIONS` maps the detected MIME to jpg/png/webp; at most `MAX_PHOTOS` 30 per scope (`tooManyPhotos`); the same file again in a scope returns the existing photo (`AddedPhoto::$duplicate`); checks run before `stage()` and again after `lock()`, `stage()` outside the lock.
- **Pipelines** `PhotoPipeline` (`openStaging` -> `stage` -> `add` -> flush -> `publish`, `discardStaging`) and `DocumentPipeline` (`store` -> `add` -> flush -> `publish`) serve import and CMS; `PublishedMedia` reverts a failed write's files. `stage()` renders first and stores the original afterwards, so an undecodable file (or a memory fatal) leaves no original; a database failure after `stage()` leaves the content-addressed original for a retry to reuse. Never add a pixel check to `PhotoPipeline` or `ImageVariantGenerator` (upload limits: `MEDIA_MAX_PIXELS` 20 MP in `Assert\Image`, `MEDIA_MAX_PORTRAIT_RATIO` 2) and never call `raiseBatchMemoryLimit()` in a request.
- **Files go last:** `RemoveVenueFiles` (best effort, never throws) runs after the commit. An original is removed only when no photo or document row of any venue uses it (`VenueRows::isOriginalUsed()`, `VenueRepository::originalsUsedOnlyBy()`: demo venues share originals). The last gallery photo may go, even from a published venue. `RemoveRoom` moves its photos, in order, to the end of the gallery; no file goes.
- **Purges:** handlers dispatch `PurgeVenueCache` / `PurgeListingsCache` / `RemoveVenueFiles` with `DispatchAfterCurrentBusStamp`, so they run after the commit and not when it failed; nobody calls `HttpCachePurger` directly, and an implementation never throws (it logs and returns): a throw after the commit would report a committed change as failed. `StoreClearingHttpCachePurger` invalidates the whole store for either method, so `purgeListings: false` saves nothing today; keep choosing it. Every write purges the venue and, by default, the listings; `purgeListings: false` for documents, `ReorderRooms`, room-scoped photo writes and the Google place commands.

## Content import

- **Command:** `make sf c="app:venues:import [path] [--dry-run] [--only=key] [--prune] [--force] [--overwrite-cms-edits]"` (`Venues\Console\ImportContentCommand`) reads `<CONTENT_ROOT>/venues/<key>/` (`CONTENT_ROOT` in `.env`, git-ignored `content/`; never commit content). Format and options: `docs/content-format.md`; schema `docs/content-format.schema.json` (top level closed, so `rating` and `reviews` are refused; enums pinned by `ContentSchemaVocabularyTest`). Nothing generates folders any more. `bin/prod-import` refuses `--prune` (an unmounted `venues/` would unpublish every unedited venue). One import at a time: no lock.
- **Format rules:** only `name`, `capacity.max`, `translations.de.summary` are required; `address.canton` is one of 27 codes (26 cantons and `li`); an omitted optional field resets to NULL on update; `ContentFormat::VERSION` (2 since F3: no `party`, no `party_note`, the ten groups; `docs/content-format.md` and the schema equal the database) is part of every content hash, so raising it re-applies every venue.
- **Flow:** one `ImportVenueContent` dispatch (one transaction) per folder; a failing folder is reported and the run goes on (exit 1). `ContentReader` validates before any write; an unchanged `content_hash` skips the venue; then `UnpublishMissingContent` (`--prune`) and `RecordContentImport`. Originals are stored and variants rendered before the first DB write; after the commit `RemoveVenueFiles`, `PurgeVenueCache` per changed or pruned venue, `PurgeListingsCache` once per run that created, updated or unpublished a venue.
- **Identity:** the key is immutable and the number stays. Rooms keep their row by `content_key`, photos by `(room key, original_path)`, documents by `path`; originals are content-addressed (`MEDIA_ROOT/content/<key>/<sha256>.<ext>`), so a renamed or reordered file keeps its id and variants and changed bytes get a new photo. Every other child set (terms, all translations) is replaced.
- **CMS guard (S8):** a venue with `cms_edited_at` set (every CMS or manager save via `close()`; cleared by `recordContentHash()` when an import applies) is reported `cms_edited` (`ImportStatus::CmsEdited`) and skipped whole, also under `--force` and `--prune`; a tombstoned key is not recreated. The handler locks the row (`PESSIMISTIC_WRITE`) before it reads the guard (not in a dry run), so a staff save cannot slip in. `--overwrite-cms-edits` applies them anyway, an unchanged hash included, and clears marker and tombstone (a deleted venue returns with a new number); never put it in a deploy script. `planPhotos()` keeps a photo in a room without a content key apart from the folder's gallery photo and drops surplus rows of one original in one scope.
- **Memory:** the import and `app:media:regenerate` call `ImageVariantGenerator::raiseBatchMemoryLimit()` first (to `BATCH_MEMORY_LIMIT` 512M, never lower; `BATCH_MEMORY_WARNING` when it cannot): a 60 MP photo is fatal at 256M. Run full imports with `--no-debug` (debug keeps about 2.5 KB per query).

## Google place ID and one-off tools

- **Rating on the page:** only the ID is stored; Google's element shows the rating in the visitor's browser (`VenueDetail::showsGoogleRating()`: ID set and not hidden). `venue_google_rating(venue)` (`Twig\VenueGoogleRatingExtension`, `%env(default::GOOGLE_MAPS_JS_KEY)%`) is `''` unless `showsGoogleRating()`; keyless only the link "Bewertungen auf Google Maps ansehen"; with a key the box `.venue-google-rating--live` that `assets/js/google-rating.js` fills, and only then it sets the main request's `_csp` attribute to `ContentSecurityPolicy::GOOGLE_PLACES` (`### Shared`); the server never sends a `gmp-` tag or a Google value. The previews override `{% block google_rating %}`; a key change needs `sh bin/prod-import purge`.
- **One-off tools** (runbooks `docs/operations.md` §Geocode the venues and §Google rating): `app:venues:geocode [--dry-run] [--limit=N]` (`VenueCoordinateFiller`, `VenueGeocoder`) writes `geo:` into `venue.yaml` files without one (a folder with `geo:` is never asked again; a wrong match is a wrong pin: read the `NO` rows of `content/owner/geocode-report.csv`, which each run replaces). The pin reaches the database only through the import, which skips `cms_edited` venues: set theirs by hand in the CMS card "Adresse & Lage". `app:venues:find-google-places [--limit]` writes `content/owner/google-places-report.csv` (nothing to the DB; `apply=yes` only on confident rows), asking Text Search with `CANDIDATE_FIELDS` (all Pro) and `pageSize` 5 inside Switzerland's box (`VenueGeocoder::candidates()`); `app:venues:apply-google-places [--dry-run]` sets the rows marked `yes` (trimmed, any case; `GooglePlaceReport::read()` refuses the geocode report; exit 1 on refused or unknown rows) through `AssignVenueGooglePlace`, counting a venue that already has an ID as `kept` before any dispatch (a second apply writes no audit row). Console output is counts, reason codes and venue numbers, never an ID or Google value. `GOOGLE_PLACES_API_KEY` lives in the shell only; the reports hold Google's names, which the Maps terms do not let us keep: git-ignored, delete them when done.
- **Decision** `GooglePlaceMatcher::decide()` (pure): the first failing check on the top candidate wins, in `GooglePlaceReason` order. `place_name_only`: every name word of ours is a place word and Google's whole name, type words included, is not exactly ours. `common_name`: no strong word, and Google's whole town not in our name (no substring, one edit or hyphen part). `far_from_pin` (> `MAX_PIN_KM` 1.0 from a non-town-centre pin) is a veto only. A name that is only a canton or district name (`Hotel Zürich`) is confident only when Google's town has that name. Words are >= 3 letters or a digit; `GENERIC` words are no name words; a word is found when equal, both >= 6 letters and one edit apart, or ours >= 5 letters inside theirs, never inside when either is `WEAK` (`linde` is not `lindenhof`); `GooglePlaceMatcherTest` pins both lists: when a confident match proves wrong, clear the ID in the CMS card and add the word with a test. `GooglePlaceFinder` makes a confident row doubtful `same_place` when its ID is another row's in this run or already held (`placeOwners()`). Reasons: `google_place.reason.<code>` in `venues` (`GooglePlaceReasonKeysTest`).
- **Accepted residual risk** (owner; confident rows are not checked by default): a `WEAK` word equal to a whole town name (`Linden`, `Aigle`), a town named like a common noun (`Dorf`), `l'Ours`-style elided articles, unlisted French or Italian inn words and `Hotel X` against `Auberge X` can still match another business.

## Read side and detail page

- **Routes:** `venue_show` `GET /eventlokal/{slug}` (`VenueDetailController`, `SLUG_REQUIREMENT`): current slug 200, a `venue_slug_history` slug 301 to the current one, unpublished (status or no default-locale translation) 410, else 404; no session; 200 and 301 get `PublicCache::page()`, the thrown 404 and 410 an hour. `venue_phone` `GET /eventlokal/{slug}/telefon` (`VenuePhoneController`): limiter `phone_reveal` (`config/packages/rate_limiter.yaml`: 20 per 10 minutes per client IP, pool `cache.phone_reveal`; 429 + `Retry-After`) runs first, so it also blocks slug enumeration; HTML, or JSON for `Accept: application/json`; `private, no-store`, `X-Robots-Tag: noindex, nofollow`, `Vary: Accept`. Tests clear that pool in `setUp()`.

## Claims (G6 `claim-verify`)

- **Preview actions:** both buttons of `venues/preview/show.html.twig` are one `<form method="post">` to `portal_claim_start` with the token in a hidden field (`intent` `claim` or `correct`); no URL carries the token.
- **`VenueClaims`** (interface, implemented by `Portal\ReadModel\PortalVenueAccessQuery`): `isConfirmed(venueId)` is true once an `active` manager row exists. `VenueDetailController` passes `unconfirmed` to the template; `_head.html.twig` shows «Noch nicht vom Betreiber bestätigt» (`.venue-head__unconfirmed`, D18). Granting, inviting, removing a manager and a verified claim dispatch `PurgeVenueCache` after the commit. Cards and listings show no label.
- **Commands:** `RevokeVenuePreviews(venueId)` ends every open link (nested by `VerifyClaim`, `GrantVenueAccess`, `InviteLocationManager`; not audited itself); `DecidePhotoCandidates(number, approvedIds, rejectedIds)` (audited) sets `photo_candidates.status`, ignoring ids of other venues (`PhotoCandidate::approve()`/`reject()`).
- **Read side:** `ReadModel\PhotoCandidateQuery::open(number)` (SQL, `PrivateImportDataTest` allows it): `candidate` rows of the venue's `fetched` records, http(s) only, at most 60. `PhotoCandidateRow::fileName()` for the list.
- **Fetching images:** `SafeFetcher::open(?FetchLimits)` and `FetchSession::image(url)` (jpeg/png/webp, any public host, no robots.txt because the operator asks; counts against `maxPages`).

**G11 (`outreach-tracking`).** `venue_previews.campaign_code` is nullable (a link sent by e-mail has none; `IssueVenuePreview::$campaignCode` is `?string`, the CMS field optional, label "Ohne Kampagne (E-Mail)") and every new link gets a `short_code` (`ValueObject\PreviewShortCode`, 10 unambiguous signs). `venue_preview_short` `/v/{code}` renders the same private preview (`VenuePreviewQuery::findByShortCode()`); the CMS QR code encodes the short link. Crm's print list issues links with a Location's campaign.
