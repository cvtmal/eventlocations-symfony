### Portal

Location managers: their accounts, their access to venues, and the staff screen over those accounts.

**Built in #42 `portal-accounts`.** Migration `Version20261101212259`; mapping `orm.mappings.Portal`; no Composer or npm package; no cron. Outcome: `docs/rpi-cycles.md` `### 42.`. A manager registers, logs in and keeps a profile; the location screens are #44's, below. S16's golden rules decide open questions: super simple, reuse everything, no 2FA.

- **Tables:** `portal_users` (`email` lower-case, `uk_portal_users_email`, `chk_portal_users_email`; `phone` `VARCHAR(40)`, the CRM's length, so #43 needs no guard when it copies it; `password_hash` and `email_verified_at` both null until the mail's link is saved; `is_active`; `last_login_at`). `portal_venue_access`, key `(portal_user_id, venue_id)`, both FKs `CASCADE`, `status` `pending` or `active`, `chk_portal_venue_access_confirmed` (`active` if and only if `confirmed_at` is set), `requested_at`, `created_at`, `updated_at`. `admin_audit_log.portal_user_id`, `ON DELETE SET NULL`, with `chk_admin_audit_log_portal_user` and `portal_user` in `chk_admin_audit_log_actor_type`.
- **Routes:** open: `portal_login` `/konto/anmelden`, `_logout_portal` POST `/konto/abmelden` (YAML, `config/routes/security.yaml`), `portal_register` `/konto/registrieren`, `portal_forgot_password` `/konto/passwort-vergessen`, `portal_reset_password` `/konto/passwort-neu/{token}`. Closed: `portal_home` `/konto`, `portal_profile` `/konto/profil` (two named forms on one route). Staff, in the `admin` firewall, `ROLE_ADMIN` by class: `admin_portal_accounts` `/admin/konten`, POST `admin_portal_accounts_{deactivate,reactivate}`.
- **Firewall, default deny:** `portal` on `^/konto(/|$)`, form login, `login_throttling` 5 per 15 minutes, logout with CSRF, no 2FA, no `user_checker`, lazy. `access_control` names the five open paths; the last line, `^/konto(/|$)`, closes everything else to `ROLE_PORTAL_USER`, so a later route is closed without an edit. `^/konto/api/` has its own line: the access listener runs before `#[IsCsrfTokenValid]`, so an anonymous JSON write never reaches the CSRF check and answers `PortalEntryPoint`'s JSON 401.
- **Session cookie, in two steps:** `framework.session.cookie_path` stays `/admin`, and public pages stay free of a session (S10). Step 1, the name: `PortalSessionStorageFactory` decorates `session.storage.factory` and sets `PortalArea::SESSION_COOKIE` (`KONTOSESSID`), because the name must be on the storage before the session starts. Step 2, the path: the session listener writes the static `/admin`, so `PortalResponseHeadersListener` (`kernel.response`, -1010, after the session listener's -1000) moves the cookie to `PortalArea::COOKIE_PATH`, for a set and for a delete. The same listener sends `Cache-Control: no-store, private` and `X-Robots-Tag: noindex, nofollow`. `PortalArea::contains()` asks the firewall map, so percent-encoded spellings and 404s under `/konto` are covered.
- **Logout sets a new `KONTOSESSID`, it does not delete one.** The logout POST passes the stateless CSRF check, and `SameOriginCsrfTokenManager` writes `csrf-token` into the session just invalidated, so the session listener sees a non-empty session with a new id. Same as `/admin`, no code against it: the old id and the new id both redirect to the login. Assert exactly that, not "the cookie is cleared".
- **A new `/konto` route:** an attribute route in `src/Portal/Controller` under `/konto/...`, name `portal_*`, `options: [LocalizedRoutes::UNLOCALIZED => true]`. No `security.yaml` edit. `PortalRoutesAreClosedTest` walks it by itself, canonical and percent-encoded, with an empty jar; `routeSample()` knows `VenueNumber::REQUIREMENT`, and another strict requirement has to be taught there, because its 404 fails the walk. The headers, `CleanText` on forms and the session arrive through `PortalArea`. A route that must be open joins `OPEN_ROUTES` in that test and an `access_control` line. The walker has one gap: a `PUBLIC_ACCESS` line for a page with `#[CurrentUser]` does not fail it, because the attribute answers the same redirect; `/konto/profil` is such a page. Staff routes of `Portal` live under `/admin/...`, named `admin_*`, with `#[IsGranted]`.
- **`PortalIdentity`:** `#[CurrentUser] PortalIdentity $identity`; `id()`, `email()`, `firstName()`, `lastName()`, `displayName()`, `initials()`; role `ROLE_PORTAL_USER`; `app.user.displayName` in Twig. A session snapshot: anything else comes through a `ReadModel`, as `PortalProfileQuery` reads the phone. `isEqualTo` compares id, e-mail and the password fingerprint, so a changed password ends every session, the manager's own included (`/konto/profil` then redirects to the login), and a changed name ends none.
- **Login:** `RefusePortalLoginListener` on `CheckPassportEvent`, -1, right after the password check, so only someone with the right password learns the state. An inactive account gets `login.error.disabled`. An account with no password gets the ordinary invalid answer, active or not: `CheckCredentialsListener` throws on a null hash, before this listener. `PortalUserProvider::loadUserByIdentifier()` does not refuse an inactive account, so that message can show; `refreshUser()` does, so deactivating ends a running session on its next request. `RecordPortalLoginListener` dispatches `RecordPortalLogin`, not audited; a login changes `updated_at`.
- **Access check:** `PortalVenueVoter::EDIT` (`'PORTAL_VENUE_EDIT'`), the one place that decides. The subject is the venue `number`, int or digit string: `IsGranted` hands over the raw route value. Only an `active` row grants. Use `#[IsGranted(PortalVenueVoter::EDIT, subject: 'number')]` with `requirements: ['number' => VenueNumber::REQUIREMENT]`, which keeps the number inside `INTEGER`. One attribute, no read and write split. A denied logged-in manager gets a 403. No route uses it in #42.
- **`portal_venue_access`, for #43 and #44:** `PortalVenueAccess(PortalUser $user, Venue $venue, \DateTimeImmutable $requestedAt)` is `pending`, `confirm($at)` makes it `active`, a rejected request deletes the row. Read side `PortalVenueAccessQuery::isActive(string $portalUserId, int $venueNumber)`, only this; #44 adds its list method there. No repository in #42, no caller; #43 adds `PortalVenueAccessRepository` and sets `repositoryClass`. Factories: `PortalVenueAccessFactory` default `pending`, state `active()`; `PortalUserFactory` default confirmed and active, states `unconfirmed()` (also no password), `deactivated()`.
- **Registration takes no password.** Register asks name and e-mail. `RegisterPortalUserHandler` creates the account with a null hash and sends the link; a known, active address with no password gets the mail again and nothing else changes; an address with a password or a deactivated one gets no mail. The link opens `portal_reset_password`, and saving calls `PortalUser::setPasswordFromMail()`, which sets the hash and `email_verified_at` in one step, keeping an earlier confirmation. Only the mailbox owner can ever set a password, and a GET changes nothing, so a mail gateway's pre-fetch is harmless. A resend is the forgot form or registering again. The forgot form on a no-password account sends the reset mail: one hour, wording "neues Passwort angefordert", slightly off for a first password, left as is.
- **`PortalLinkSigner`:** signed links, no token table, one `SignatureHasher`. `registrationToken()` 48 h, `resetToken()` 1 h, `resetUserId()`; a token is `<uuid>.<expires>.<hash>`. The signature holds `userIdentifier` and `password`, so a used link and an open form die with the hash; a null hash signs an empty value, and every link dies once a password is set. `TOKEN` is strict on the UUID because 36 dashes would reach a Postgres `UUID` column as a 500. A bad token is null; the caller answers 410.
- **Notice page (D1):** `portal/security/notice.html.twig` takes `title`, `text`, `link` (catalogue keys) and `link_route`. Its one caller is `ResetPasswordController`: a bad link answers on it with 410 and no redirect, because the cookie is `SameSite=Strict`: a click from webmail is cross-site, so a flash after a redirect would come late or never. The path starts no session. `validate-html`'s `curl -f` cannot read a 410; check that page another way.
- **Abuse:** limiter `portal_register`, sliding window, 5 per hour per IP, pool `cache.portal_register`, shared by register and forgot, autowired as `$portalRegisterLimiter`. 429 text `register.error.rate_limited`. The block is copied in the two controllers, not extracted. Honeypot `website` on registration only; it gets the normal answer, stores nothing and costs no budget. A known and an unknown address get the same answer; on registration only a known, active address with no password gets a mail. `PortalEmailTaken` (lost race on `uk_portal_users_email`) ends in the normal answer too.
- **Mail:** `PortalMailer::sendRegistrationLink()`, `sendPasswordReset()`, on `templates/emails/layout.html.twig`, under `templates/portal/email/`. `send()` catches `TransportExceptionInterface`, `RfcComplianceException` and `HandlerFailedException`, logs the account id, class and place, and swallows: a dead mail server changes no answer. New methods catch the same three. The context holds `token` only, and the greeting is a plain "Guten Tag": the address is unproved, so a mail that quoted the visitor's text would carry anything to a stranger from our domain.
- **Forms and strings:** `PortalTextConstraintExtension` puts `CleanText` on every text field under `/konto`, staff forms stay with Admin's. Flashes in `portal` templates: `$this->addFlash('success', PortalFlash::message('flash.key'))`, since `_flash` hard-codes domain `admin`; a plain key shows untranslated. Passwords: `PortalPasswordHasher::hash()`, `MIN_LENGTH` 8, length owned by the forms, help text `register.password_help` with `{min}`. Catalogue `translations/portal+intl-icu.de.yaml`, "Sie", staff strings under `accounts.*` neutral. #42 holds `shell`, `login`, `register`, `forgot`, `reset`, `overview`, `profile`, `accounts`, `mail`, `flash`; a later cycle adds its own prefix (`claims`, `review`, `editor`, `onboarding`), which keeps parallel edits apart.
- **Look:** `templates/portal/base.html.twig`, a copy of the back-office shell. Blocks `title`, `body_class`, `breadcrumbs`, `page_actions`, `page_header`, `aside`, `main`, `scripts`. Usable: `templates/admin/components/*`, `admin_icon`, `admin_query_path`, `admin_page_links`, `csp_nonce`, `swiss_number`, form theme `admin/form/theme.html.twig`, `admin_island_assets()`, `_scripts`. Not usable: `_sidebar`, `_search_trigger`, `admin_navigation`, `app.user.role`. `_sidebar.html.twig` here holds "Meine Locations", "Profil", the user block and logout, with no extension points; #44 changes only the active state for `/konto/locations/*`. `base_auth.html.twig` extends `admin/base_auth.html.twig`, blocks `title`, `body`, `form`. At 390 px the sidebar stacks above the content, like `/admin/benutzer`. It uses `.shell` from `assets/styles/admin/_layout.scss`, so it stays.
- **Audit:** `App\Shared\Security\PortalActor`, `id(): string`, lives in Shared because Admin may not name Portal. `PortalIdentity` and `PortalUser` implement it, and `doctrine.yaml`'s `resolve_target_entities` maps it to `PortalUser` for `AuditLogEntry::$portalActor`. `AuditLogMiddleware` logs any logged-in `PortalActor` as `AuditActorType::PortalUser`, so a command implementing `AuditableCommand` is all a cycle does. Audited in #42: `UpdatePortalProfile` (its summary holds the new name and phone, shown to admins), `ChangePortalPassword`, `DeactivatePortalUser`, `ReactivatePortalUser`. The logged-out commands are not. `AuditLogQuery`, `VenueHeaderQuery` and `VenueListQuery` read the name through `LEFT JOIN portal_users` and `COALESCE` with staff, a deleted manager shows "Gelöschtes Konto". `TimelineQuery` gets it through `AuditLogQuery::forSubjects()`. `AuditLogFilter::$actorId` filters `actor_id` only, so the audit screen's actor filter cannot pick a manager. #44's staff widget filters on `actor_type = 'portal_user'`.
- **Staff screen:** `AccountsController`, `PortalAccountListQuery` (`PER_PAGE` 50, `geo_search_key()` over name and e-mail, no index), `PortalAccountRow`, `PortalAccountPage`, `PortalAccountFilterType`, which brings `CleanText` to `q`. `PortalAccountsNavigationItem`: section Settings, priority 250, `ROLE_ADMIN`. Row actions are hand-written `<form>`s with `deactivate[_token]`, because `form_start()` in 50 rows repeats an id; `PortalUserNotFound` from the handler answers 404.
- **Module rule:** `Portal` in `ArchitectureRules::MODULES`, may depend on Admin, Cms, Venues, Geo, Media and Shared. `ModuleBoundariesTest` denies Search, Favorites, Inquiries, Seo and Crm. `Crm` may depend on `Portal`; nothing else may. #43's `Crm\EventListener` on `Portal\Event\…` fits this.

A class with both traits names the winner, `AdminSession::setUp insteadof PortalSession` and the same for `tearDown`; Admin's `setUp` does not clear `cache.portal_register`, so a test there that posts to register or forgot calls `forgetPortalThrottling()` first. `logInFully` and `submitManagerLogin` work in one client (`PortalAdminSeparationTest`). `sendSessionCookieEverywhere()` moves a cookie's path and keeps its name, so it never reaches the other area's reader: to ask the other firewall, send the id under the name that area reads, `MOCKSESSID` or `KONTOSESSID` in the test env, and assert the session was read (`presentSessionAs()`, `assertRequestReadTheSessionOf()`).
- **Test traps:** after a login the `PortalUser` from `createManager()` or `logInAsManager()` is no longer managed, so `deactivate()` plus `flush()` writes nothing; re-read it with `find()`. `PortalUserFactory` has no `phone` attribute: use SQL or `updateProfile()`. **Built in #44 `portal-editor`.** No migration, no package, no new island. Outcome: `docs/rpi-cycles.md` `### 44.`. A manager maintains a location at `/konto/locations/{number}`: seven cards, Fotos, Vorschau, Offline nehmen. Every write is an existing `Venues` command plus `ChangeVenueCapacity`, so the audit, the import guard and the purge come with it. Going back online is #45's.

- **Routes, each behind `#[IsGranted(PortalVenueVoter::EDIT, subject: 'number')]` and `VenueNumber::REQUIREMENT`:** `portal_location` GET, POST `portal_location_{texts,address,terms,wedding,contact,faq,capacity}` (`/texte`, `/adresse`, `/merkmale`, `/hochzeit`, `/kontakt`, `/faq`, `/gaeste`), `portal_location_photos` `/fotos`, `portal_location_preview` `/vorschau`, POST `portal_location_offline` `/offline`. The voter decides; no controller reads an access row.
- **Cards:** `ValueObject\LocationCard`, the manager's copy of `Cms\ValueObject\VenueCard`: `texts, address, terms, wedding, contact, faq, capacity`, no `basics`, no `rating`, each naming its form, data class and route; `template()` because the capacity card lives in `templates/portal/location/`. `Form\LocationForms` is `VenueEditorForms` for those cases, with `town_lookup_url` on `portal_api_towns`, and adds `offlineForm()`. `VenueCapacityType` and `VenueCapacityData` hold the maximum alone. `allow_extra_fields` stays off, so a crafted name, slug, tier or `capacityMin` is a 422 with nothing changed.
- **Lowering the maximum:** `ChangeVenueCapacityHandler` clears a staff minimum above the new maximum, because `chk_venues_capacity` would refuse it. The manager cannot see that field, so there is no message.
- **Cms services, and what each keeps:** `Cms\Form\VenueCardSaver` holds the save and returns `VenueCardSaveOutcome` (`Saved`, `Unchanged`, `Invalid`, `Stale`); the caller keeps the flash, the redirect and the render. `VenueNotFound` stays a `NotFoundHttpException` there. `Cms\VenuePhotoUpload` holds the upload's checks and limits; `add(…, bool $roomsAllowed = true)`, and `Portal` passes `false`, so a manager's upload lands in the gallery whatever the body says. Cms's `PhotoUploadController` keeps its attributes and `MAX_SIZE`, `MAX_BYTES` as aliases. `Cms\TownOptions` holds the lookup's query rules; each controller keeps its route and its firewall. `VenueListQuery::byNumbers()` keeps `$missing`'s SQL in Cms: the overview reads `PortalVenueAccessQuery::activeNumbers()` and passes the numbers.
- **JSON guards:** `PortalEntryPoint` and `PortalAccessDeniedHandler`, shaped like Admin's. Under `PortalArea::JSON_PATH`, `/konto/api/`, an anonymous call is a JSON 401 and a refused one a JSON 403; a page keeps the login redirect and the default 403 page. They are the two `security.yaml` lines of the named exception, because a bad CSRF token would otherwise be a redirect to the login.
- **`portal_api`:** the `csrf-token` meta in `base.html.twig` is the first session-stored token on `/konto`; login, register and the rest extend `base_auth`, so it starts no anonymous session. Header `X-CSRF-Token`, `#[IsCsrfTokenValid('portal_api', …)]` on the two API controllers. `TownLookupController` is a GET and takes none.
- **`portal_upload`:** sliding window, 60 per hour per manager id, pool `cache.portal_upload`, one check in `Api\PhotoUploadController`, before `VenuePhotoUpload`. It answers a **JSON 422 on `file`**, `portal.photo.rate_limited`, not a 429: `admin-ui/src/cms/upload.js` shows a text only for a 422, and a 429 would invite a retry. Every attempt counts, a refused file too. Staff are not limited.
