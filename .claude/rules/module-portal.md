### Portal

Location managers: their accounts, their access to venues, and the staff screen over those accounts.

**Built in #42 `portal-accounts`.** Migration `Version20261101212259`; mapping `orm.mappings.Portal`; no Composer or npm package; no cron. Outcome: `docs/rpi-cycles.md` `### 42.`. A manager registers, logs in and keeps a profile; asking for access is #43's and the location screens are #44's, both below. S16's golden rules decide open questions: super simple, reuse everything, no 2FA.

- **Tables:** `portal_users` (`email` lower-case, `uk_portal_users_email`, `chk_portal_users_email`; `phone` `VARCHAR(40)`, the CRM's length, so #43 needs no guard when it copies it; `password_hash` and `email_verified_at` both null until the mail's link is saved; `is_active`; `last_login_at`). `portal_venue_access`, key `(portal_user_id, venue_id)`, both FKs `CASCADE`, `status` `pending` or `active`, `chk_portal_venue_access_confirmed` (`active` if and only if `confirmed_at` is set), `requested_at`, `created_at`, `updated_at`. `admin_audit_log.portal_user_id`, `ON DELETE SET NULL`, with `chk_admin_audit_log_portal_user` and `portal_user` in `chk_admin_audit_log_actor_type`.
- **Routes:** open: `portal_login` `/konto/anmelden`, `_logout_portal` POST `/konto/abmelden` (YAML, `config/routes/security.yaml`), `portal_register` `/konto/registrieren`, `portal_forgot_password` `/konto/passwort-vergessen`, `portal_reset_password` `/konto/passwort-neu/{token}`. Closed: `portal_home` `/konto`, `portal_profile` `/konto/profil` (two named forms on one route). Staff, in the `admin` firewall, `ROLE_ADMIN` by class: `admin_portal_accounts` `/admin/konten`, POST `admin_portal_accounts_{deactivate,reactivate}`.
- **Firewall, default deny:** `portal` on `^/konto(/|$)`, form login, `login_throttling` 5 per 15 minutes, logout with CSRF, no 2FA, no `user_checker`, lazy. `access_control` names the five open paths; the last line, `^/konto(/|$)`, closes everything else to `ROLE_PORTAL_USER`, so a later route is closed without an edit. `^/konto/api/` has its own line: the access listener runs before `#[IsCsrfTokenValid]`, so an anonymous JSON write never reaches the CSRF check and answers `PortalEntryPoint`'s JSON 401.
- **Session cookie, in two steps:** `framework.session.cookie_path` stays `/admin`, and public pages stay free of a session (S10). Step 1, the name: `PortalSessionStorageFactory` decorates `session.storage.factory` and sets `PortalArea::SESSION_COOKIE` (`KONTOSESSID`), because the name must be on the storage before the session starts. Step 2, the path: the session listener writes the static `/admin`, so `PortalResponseHeadersListener` (`kernel.response`, -1010, after the session listener's -1000) moves the cookie to `PortalArea::COOKIE_PATH`, for a set and for a delete. The same listener sends `Cache-Control: no-store, private` and `X-Robots-Tag: noindex, nofollow`. Lifetime: `KONTOSESSID` stays a browser-session cookie (`cookie_lifetime: 0`; `Admin\EventListener\AdminSessionCookieListener` does not reach `/konto`) with a 2-hour idle timeout, `PortalIdleTimeoutListener` (request, 16, session key `portal.last_seen`, no flash). It times only a session that holds the portal token, so a stale cookie is still deleted. It exists because the shared store keeps every file 30 days for the back office (admin-session-30-days); `PortalIdleTimeoutTest` pins 7200 s. `PortalArea::contains()` asks the firewall map, so percent-encoded spellings and 404s under `/konto` are covered.
- **Logout sets a new `KONTOSESSID`, it does not delete one.** The logout POST passes the stateless CSRF check, and `SameOriginCsrfTokenManager` writes `csrf-token` into the session just invalidated, so the session listener sees a non-empty session with a new id. Same as `/admin`, no code against it: the old id and the new id both redirect to the login. Assert exactly that, not "the cookie is cleared".
- **A new `/konto` route:** an attribute route in `src/Portal/Controller` under `/konto/...`, name `portal_*`, `options: [LocalizedRoutes::UNLOCALIZED => true]`. No `security.yaml` edit. `PortalRoutesAreClosedTest` walks it by itself, canonical and percent-encoded, with an empty jar; `routeSample()` knows `VenueNumber::REQUIREMENT`, and another strict requirement has to be taught there, because its 404 fails the walk. The headers, `CleanText` on forms and the session arrive through `PortalArea`. A route that must be open joins `OPEN_ROUTES` in that test and an `access_control` line. The walker has one gap: a `PUBLIC_ACCESS` line for a page with `#[CurrentUser]` does not fail it, because the attribute answers the same redirect; `/konto/profil` is such a page. Staff routes of `Portal` live under `/admin/...`, named `admin_*`, with `#[IsGranted]`.
- **`PortalIdentity`:** `#[CurrentUser] PortalIdentity $identity`; `id()`, `email()`, `firstName()`, `lastName()`, `displayName()`, `initials()`; role `ROLE_PORTAL_USER`; `app.user.displayName` in Twig. A session snapshot: anything else comes through a `ReadModel`, as `PortalProfileQuery` reads the phone. `isEqualTo` compares id, e-mail and the password fingerprint, so a changed password ends every session, the manager's own included (`/konto/profil` then redirects to the login), and a changed name ends none.
- **Login:** `RefusePortalLoginListener` on `CheckPassportEvent`, -1, right after the password check, so only someone with the right password learns the state. An inactive account gets `login.error.disabled`. An account with no password gets the ordinary invalid answer, active or not: `CheckCredentialsListener` throws on a null hash, before this listener. `PortalUserProvider::loadUserByIdentifier()` does not refuse an inactive account, so that message can show; `refreshUser()` does, so deactivating ends a running session on its next request. `RecordPortalLoginListener` dispatches `RecordPortalLogin`, not audited; a login changes `updated_at`.
- **Access check:** `PortalVenueVoter::EDIT` (`'PORTAL_VENUE_EDIT'`), the one place that decides. The subject is the venue `number`, int or digit string: `IsGranted` hands over the raw route value. Only an `active` row grants. Use `#[IsGranted(PortalVenueVoter::EDIT, subject: 'number')]` with `requirements: ['number' => VenueNumber::REQUIREMENT]`, which keeps the number inside `INTEGER`. One attribute, no read and write split. A denied logged-in manager gets a 403. No route uses it in #42.
- **`portal_venue_access`, for #43 and #44:** `PortalVenueAccess(PortalUser $user, Venue $venue, \DateTimeImmutable $requestedAt)` is `pending`, `confirm($at)` makes it `active`, a rejected request deletes the row. Read side `PortalVenueAccessQuery`: `isActive(string $portalUserId, int $venueNumber)` and #44's `activeNumbers(string $portalUserId)`. Write side `PortalVenueAccessRepository` (#43, set as `repositoryClass`): `findAccess()`, and `insertPending()` with `ON CONFLICT DO NOTHING`. Factories: `PortalVenueAccessFactory` default `pending`, state `active()`; `PortalUserFactory` default confirmed and active, states `unconfirmed()` (also no password), `deactivated()`.
- **Registration takes no password.** Register asks name and e-mail. `RegisterPortalUserHandler` creates the account with a null hash and sends the link; a known, active address with no password gets the mail again and nothing else changes; an address with a password or a deactivated one gets no mail. The link opens `portal_reset_password`, and saving calls `PortalUser::setPasswordFromMail()`, which sets the hash and `email_verified_at` in one step, keeping an earlier confirmation. Only the mailbox owner can ever set a password, and a GET changes nothing, so a mail gateway's pre-fetch is harmless. A resend is the forgot form or registering again. The forgot form on a no-password account sends the reset mail: one hour, wording "neues Passwort angefordert", slightly off for a first password, left as is.
- **`PortalLinkSigner`:** signed links, no token table, one `SignatureHasher`. `registrationToken()` 48 h, `resetToken()` 1 h, `resetUserId()`; a token is `<uuid>.<expires>.<hash>`. The signature holds `userIdentifier` and `password`, so a used link and an open form die with the hash; a null hash signs an empty value, and every link dies once a password is set. `TOKEN` is strict on the UUID because 36 dashes would reach a Postgres `UUID` column as a 500. A bad token is null; the caller answers 410.
- **Notice page (D1):** `portal/security/notice.html.twig` takes `title`, `text`, `link` (catalogue keys) and `link_route`. Its one caller is `ResetPasswordController`: a bad link answers on it with 410 and no redirect, because the cookie is `SameSite=Strict`: a click from webmail is cross-site, so a flash after a redirect would come late or never. The path starts no session. `validate-html`'s `curl -f` cannot read a 410; check that page another way.
