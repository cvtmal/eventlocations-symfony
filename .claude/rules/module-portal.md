### Portal

Location managers at `/konto`: accounts, firewall and session cookie, signed links, venue access, editor, onboarding wizard, and their staff screens. Read it by hand for any `/konto` route or `security.yaml` edit. S16 (`docs/rpi-cycles.md`) decides open questions: super simple, reuse everything, no 2FA, no wizard table, no token table.

## Boundaries

- **One write path:** editor and wizard dispatch existing `Venues` commands, so audit, import guard and purge come along; staff-only: name, slug, tier, Google place ID, deletion (rooms and documents are the manager's since F11).
- **Address:** `/konto` and Portal mails say "du" (E4); staff strings (`accounts.*`, `review.*`, `invite.panel`/`flash`, `onboarding.queue.*`) are neutral and say "Eintrag" for the venue, `/konto` "Location".

## Data model

Baseline migration `Version20261106174839`, mapping `orm.mappings.Portal`.

- **`portal_users`:** `email` lower-case (`chk_portal_users_email`, `uk_portal_users_email`), `phone` `VARCHAR(40)` (the CRM's length), `password_hash` and `email_verified_at` null until the mail's link is saved, `last_login_at`.
- **`portal_venue_access`:** `(portal_user_id, venue_id)`, `pending|active`, `chk_portal_venue_access_confirmed` (`active` iff `confirmed_at` is set); a rejected request deletes the row.
- **`portal_submissions`:** one row per venue, `draft|submitted|rejected|accepted` (`chk_portal_submissions_status`), `submitted_by` `SET NULL`, `reviewed_by` `RESTRICT`, `rights_confirmed_at`, `reject_reason` (1000); `venues.status` stays the online switch. A claimed (imported) location has no row until its first submit.
- **`admin_audit_log.portal_user_id`:** `SET NULL`, `chk_admin_audit_log_portal_user`, `portal_user` in `chk_admin_audit_log_actor_type`.

## Firewall, session cookie and route conventions

- **Firewall `portal`:** `^/konto(/|$)`, default deny, `login_throttling` 5 per 15 minutes, CSRF logout, no 2FA. In `access_control` (first match wins) the five open paths come first and `^/konto(/|$)` for `ROLE_PORTAL_USER` closes the rest. `^/konto/api/` has its own line: the access listener runs before `#[IsCsrfTokenValid]`, and an anonymous JSON write must get `PortalEntryPoint`'s JSON 401, not reach the CSRF check.
- **Session cookie:** `cookie_path` stays `/admin`; public pages stay free of a session (S10). `PortalSessionStorageFactory` sets the name `KONTOSESSID` before the session starts; `PortalResponseHeadersListener` (`kernel.response`, -1010, after the session listener's -1000, which writes the static path `/admin`) moves the cookie to `/konto` and sets `Cache-Control: no-store, private` and `X-Robots-Tag: noindex, nofollow` on every `/konto` response. Listeners use `PortalArea::contains()` (firewall map). No path into `/admin`: own provider, identity, cookie (`PortalAdminSeparationTest`).
- **Lifetime and logout:** browser-session cookie, 2-hour idle timeout in `PortalIdleTimeoutListener` (`PortalIdleTimeoutTest` pins 7200 s) because the shared store keeps files 30 days for the back office; only a session with the portal token is timed, so a stale cookie is still deleted. Logout sets a new `KONTOSESSID` instead of deleting one (the stateless CSRF check re-opens the session); assert that both ids redirect to the login.
- **A new `/konto` route:** attribute route in `src/Portal/Controller`, `/konto/...`, `portal_*`, `options: [LocalizedRoutes::UNLOCALIZED => true]`; no `security.yaml` edit. `PortalRoutesAreClosedTest` and `LocationRoutesAccessTest` walk it by themselves; teach any new strict requirement to their `routeSample()` (knows `VenueNumber::REQUIREMENT`, `WizardStep::REQUIREMENT`) or its 404 fails the walk. An open route joins `OPEN_ROUTES` plus an `access_control` line. Gap: `PUBLIC_ACCESS` on a page with `#[CurrentUser]` passes the walker.
- **Access check:** `PortalVenueVoter::EDIT` (`'PORTAL_VENUE_EDIT'`) alone decides; only an `active` row grants. Subject: the venue `number` (int or digit string; `IsGranted` passes the raw route value): `#[IsGranted(PortalVenueVoter::EDIT, subject: 'number')]` with `requirements: ['number' => VenueNumber::REQUIREMENT]` (keeps it inside `INTEGER`). Denied = 403; no controller reads an access row itself; `ManagerAccessQuery::statuses()` is for pills and "already" answers, never a right.
- **Identity and login:** `#[CurrentUser] PortalIdentity` is a session snapshot; other data (the phone) comes through a `ReadModel` (`PortalProfileQuery`). `isEqualTo()` compares id, e-mail and password fingerprint: a changed password ends every session, the manager's own included. `RefusePortalLoginListener` (`CheckPassportEvent`, -1, after the password check) lets only someone with the right password learn the state (inactive: `login.error.disabled`; no password: the ordinary invalid answer). `loadUserByIdentifier()` accepts an inactive account (so that message can show), `refreshUser()` refuses it: deactivating ends a running session on its next request. `RecordPortalLoginListener` dispatches `RecordPortalLogin` (not audited).
- **JSON and CSRF:** under `/konto/api/` the firewall's `entry_point` (`PortalEntryPoint`) answers anonymous with a JSON 401 and its `access_denied_handler` (`PortalAccessDeniedHandler`) refused with a JSON 403; a bad CSRF token is a 403 too. The `csrf-token` meta in `base.html.twig` is the first session-stored token on `/konto` (not in `base_auth`: anonymous pages start no session); header `X-CSRF-Token`, `#[IsCsrfTokenValid('portal_api', ...)]` on the two API controllers.

## Accounts, signed links and mails

- **Registration takes no password:** name and e-mail only; `RegisterPortalUserHandler` creates the account with a null hash and mails the link. A known, active address with no password gets the mail again; one with a password, or a deactivated one, gets none. Saving a password through the link (`setPasswordFromMail()` sets hash and `email_verified_at` together) logs in (`PortalLinkLogin`, also for reset and invitation; the firewall's session strategy migrates the id, so a planted one does not survive: `ManagerInviteTest`). Only the mailbox owner can set a password, and a GET changes nothing (mail gateways pre-fetch).
- **`PortalLinkSigner`:** signed links, no token table: `registrationToken()` 48 h, `resetToken()` 1 h, `invitationToken($userId)` 7 days (null unless the account is active with no password, so never a long reset link). The signature holds `userIdentifier` and `password`: a used link and an open form die with the hash, a null hash signs an empty value, so every link dies once a password is set. `TOKEN` is strict on the UUID (36 dashes would reach a Postgres `UUID` column as a 500). A bad token is null; the caller answers 410.
- **Dead link:** `notice.html.twig` (`title`, `text`, `link`, `link_route`) answers 410 in place, no redirect, no flash: the cookie is `SameSite=Strict`, so a click from webmail (cross-site) would lose a flash after a redirect. `validate-html` cannot read a 410.
- **Abuse:** limiter `portal_register` (sliding window, 5 per hour per client IP, pool `cache.portal_register`) is one budget for register and forgot, consumed after the form is valid; 429 plus `Retry-After`. Honeypot `website` on registration only: normal answer, nothing stored, no budget. No enumeration: known and unknown addresses get the same answer, `PortalEmailTaken` (lost race on `uk_portal_users_email`) included.
- **`PortalMailer`** catches `TransportExceptionInterface`, `RfcComplianceException` and `HandlerFailedException`, logs account id, class and place (never the exception's message, which can quote the address, and never the token) and swallows: a dead mail server changes no answer. Registration and reset mails carry `token` only and greet with a plain "Hallo": the address is unproved, so a name or visitor text in the mail would let a stranger send text from our domain. Every other mail to a person goes to a proved or staff-typed address, greets "Hallo {name}" and answers `bool`; a failed send keeps the decision and gives staff an `error` flash, because the person must be told by hand. Methods: `sendRegistrationLink()`, `sendPasswordReset()`, `sendAccessApproved()`/`sendAccessRejected()`, `sendInvitation()`/`sendManagerAdded()`, `sendLocation{Submitted,Accepted,Rejected}()`, and the staff notices `sendAccessRequestNotice()`/`sendLocationNotice()` to `site.contact_email` (fixed greeting).
- **Forms and strings:** `PortalTextConstraintExtension` puts `CleanText` on every `/konto` text field. Flashes: `PortalFlash::message('flash.key')` (`_flash` hard-codes domain `admin`). `PortalPasswordHasher::MIN_LENGTH` 8. Catalogue `translations/portal+intl-icu.de.yaml`, prefixes `shell`, `login`, `register`, `forgot`, `reset`, `overview`, `profile`, `accounts`, `mail`, `flash`, `claims`, `review`, `editor`, `onboarding`, `invite`; a new feature adds its own top-level prefix.

## Access requests and invitation

- **Requests:** a manager asks for a published location with one button; staff decide in `admin_portal_review`. `RequestVenueAccess`, `GrantVenueAccess`, `RevokeVenueAccess` are auditable on subject `portal_user`; a rejected request and a removed manager both end in `RevokeVenueAccess` (may ask again); `insertPending()` is `ON CONFLICT DO NOTHING` and answers `bool`.
- **Read first:** `ClaimController::ask()`, `ReviewController` and `VenueManagersController` read `ManagerAccessQuery::statuses()` before dispatching, since a no-op command still writes an audit row; approve and reject refuse anything but a pending row, and approve refuses a deactivated account (`invite.flash.deactivated`; the row shows "Konto deaktiviert" and only "Ablehnen"). `VenueManagersPanel` is built on `.crm-panel__*` (`assets/styles/crm/_panel.scss`), so a Crm restyle moves it. `/konto/locations/suchen` is a plain `.table`, not `.table--list` (`nowrap` hides the action at 390 px; `ClaimSearchTest`).
- **Mail and event:** `sendAccessRequestNotice()` (to `site.contact_email`) goes after the dispatch in `ask()`, only when `RequestVenueAccessHandler` answers the venue name (it wrote the row), so the second of two parallel clicks mails nobody. `LocationManagerConfirmed` goes through `PortalEvents::managerConfirmed()`, which catches `\Throwable` and logs class and place, so a subscriber cannot fail staff's response; order: command (commits), mail, event.
- **Invitation:** staff add a manager by an address with no account (`VenueManagersController::add()`): unknown address needs both names, then `InviteLocationManager` (auditable; account with no password plus an `active` access row in one flush; a lost race is `PortalEmailTaken::onInvitation()`); deactivated is refused; an existing manager is left alone unless the invitation is open (`password_hash IS NULL`), then it is mailed again with no command and no audit row. Mail after the commit, then the event; a failed mail keeps the access. A removed manager's account and link stay valid (`/konto` opens step 1); staff deactivate the account to kill the link.
- **Extension points:** `AccessRequestsNavigationItem` (Cms section, 250), `AccessRequestsWidget` (450, `LIMIT` 5), `VenueManagersPanel` (50), `PortalAccountsNavigationItem` (Settings, 250, `ROLE_ADMIN`), `LocationChangesWidget` (150).
- **Read side:** `PortalVenueAccessQuery` (`isActive()`, `activeNumbers()`, `hasAnyRow()`), `ManagerAccessQuery`, `PortalAccessRequestQuery`, `PortalAccessRequestBadge` (memo per request, `reset()`; `total()`, requests plus submissions, is the sidebar count, `count()` the requests only, for the widget), `VenueManagersQuery` (`forVenue()` active rows only), `PortalAccountListQuery` (`PER_PAGE` 50). The account list's row actions are hand-written `<form>`s (`deactivate[_token]`): `form_start()` in 50 rows repeats an id.

The right code finds or creates the account of that address (no password) and, under a venue row lock: `granted` (active row, all preview links revoked, purge) only when `ValueObject\ClaimDomain::matches()` and nobody else has a row; otherwise a pending row in #43's queue (`sendAccessRequestNotice()` only when this verification wrote it, `ClaimVerification::$wroteRequest`); a row that met somebody else's row is `competing` (`portal_venue_access.competing`, same migration). Funnel: `claim_started` at the code, `claim_verified` at every right code (any outcome but deactivated), with the link's campaign.
- **Domain rule (`ClaimDomain`):** the address's domain equals the website host without `www.` exactly, and the website is a home page (no path or a language segment like `/de/`), so a hall that is one page of a university or a city site never hands its addresses the entry; IDN non-transitional (`ß` stays `ß`); IP hosts, one label and `GENERIC` (mail providers, social and hosting platforms, also their subdomains) never match. No public suffix list: subdomain addresses, siblings under a shared suffix and a site on a subdomain go to staff.
- **Freeze:** `PortalVenueAccessQuery::isActive()` is false while the venue has a pending `competing` row, so a competing claim locks every manager out (editor, offline and photo routes alike) until staff approve or reject; a plain #43 request freezes nothing. `activeLocations()` (number => frozen, one statement) drives the overview's amber pill (no link, no resume button). `isConfirmed()` (D18) counts active rows of active accounts only.
- **After the code:** login through `PortalLinkLogin` (an account with a password logs in at once: the code proved the mailbox, like a reset link); the session id is migrated right after the code; `granted` goes to the photo step (both intents), `queued` to `/konto` with a flash. `start` refuses a `Sec-Fetch-Site` other than `same-origin` (403): no CSRF token can exist yet. A claim on a published entry mails the proof of publication at once; an unpublished one gets it from staff's acceptance.
