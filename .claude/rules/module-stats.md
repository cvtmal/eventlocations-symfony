### Stats

Cookieless statistics, no third party, no consent banner (S17; ops: `docs/operations.md`, Statistik): beacon, day-file spool, ingest, rollup, and the read models for `/admin/statistik`, `/konto` and the media kit. Read it by hand before touching a `data-stats-*` attribute, the `stats_page` block, anything stored per visitor, or a figure.

## Flow and boundaries

- Stats uses `Venues` and `Inquiries` only; only `Cms` and `Portal` may use Stats (`ModuleBoundariesTest`). Favorites knows nothing of it: `merkliste.js` fires `merkliste:add`.
- `stats.js` -> `POST /_stats` -> `CollectController` -> `var/stats/spool/<Y-m-d>.ndjson` (Zurich day; `stats.dir` = `var/stats`). `app:stats:ingest` (`bin/cron-daily` step `stats-ingest`, 03:15, or the staff button) fills raw `stats_events` and rebuilds `stats_daily`, the only table screens read. They say "Stand: <last ingest>", not "bis gestern": the button can load today.
- **No command on the beacon path** (deviation from `cqrs.md`): the bus transaction connects to Postgres and would wake Neon on every page view. `CollectControllerTest::test_collecting_never_connects_to_the_database` pins it: no firewall on `/_stats`, `flock` limiter lock, file pool `cache.stats_collect`, no Shared, Admin or Portal listener may query there.

## Privacy

- **Never stored:** the IP (no file, no table), cookies, browser storage, the query string, a referrer path. Stored per event: time, page type, path, referrer host, user agent, venue numbers, visitor hash. `stats.js` sends nothing under `navigator.globalPrivacyControl`. Raw `stats_events` are kept forever. The `/datenschutz` text (`legal.privacy.stats`, `translations/shared*`) promises this: change both together.
- **`VisitorHash::of()`** = first 32 hex of HMAC-SHA-256(`ip."\n".ua`, salt of the Zurich day). The salt is 32 random bytes in `var/stats/salt/<Y-m-d>`, created with `fopen($path, 'x')`; the loser of a race retries 20 x 5 ms, then replaces it. The prune deletes past days' salts, so no hash links to an IP afterwards. Visitor counts add each day's distinct hashes: a returning visitor counts again.

## Beacon, ingest, rollup

- **Beacon** `_stats_collect` `POST /_stats` (unlocalized, in `RobotsController::DISALLOW`; wire format in `BeaconPayload`). Limits: 50 events, 100 numbers per `imp`, texts 255, body 8192 bytes (`MAX_BODY_BYTES`), `stats_collect` 120 per 10 minutes per IP. A bad event is dropped, the rest kept; over a limit or nothing valid: 204, nothing written; foreign origin (`Sec-Fetch-Site` not `same-origin`, else `Origin` not ours): 403. Always `private, no-store`, `X-Robots-Tag: noindex, nofollow`, no session, no cookie.
- **Ingest** (`IngestStatsHandler`, bus transaction, advisory lock `stats_ingest`): claims every day file, today's open one too, by renaming it to `<Y-m-d>.<8 hex>.claimed`; loads each claimed file not in `stats_ingest_files` and logs its name; rebuilds the touched days; then `PruneStatsSpool` (after the commit, every run) deletes logged files and past salts. A crash leaves an unlogged `.claimed` file for the next run; no line loads twice. `SpoolEvent` repeats the column rules in its constructor, so a line that parses always inserts: change both together.
- **Spool:** `Spool::append` re-checks its inode after `flock` and reopens (3 tries, then `\RuntimeException`) when an ingest renamed the file; `read()` locks first (a writer that locked before the rename finishes); `SpoolReader::path()` accepts only day and claimed file names.
- **Rollup:** a day is deleted and recomputed whole, never added to. Site rows have `venue_number` 0; venue rows count only numbers in `venues.number`, so a forged one makes no row; `inquiry` has 0 visitors. `automated` events (`w=1`, sent under `navigator.webdriver`) count nowhere; no other bot filter exists, and a later one can recompute history.
- **Tables:** `chk_stats_events_{type,kind,page}` and `chk_stats_daily_metric` must list the values of `EventType`, `ClickKind`, `PageType`, `Metric` in order (`StatsVocabularyChecksTest`). The entities exist for the mapping only; writes are DBAL.
- **Inquiries:** `RecordInquiryListener` (on `InquirySubmitted`) appends an `inquiry` line and catches `\Throwable` itself, logging class, file and line, never the message: a throwing subscriber would stop the CRM's.

## Read models

- `SiteStatsQuery` (`summary`, `dailyPageViews`, `dailyVisits`, `pageTypes`, `venues`, `months`, `lastIngestAt`) and `VenueStatsQuery` (`summary`, `dailyDetailViews`) return `SiteSummary`, `DailyPoint`, `PageTypeRow`, `VenueRow`, `MonthRow`, `VenueSummary`; arguments are date-only (both ends inclusive), gaps zero-filled, midnight Europe/Zurich. `StatsPeriod` 7/30/90/365 days, today included: `fromQuery()` reads `?zeitraum=` (unknown -> 30; callers use `query->all()`, so `zeitraum[]=` falls back, no 400); `firstDay()`, not `from()` (a backed enum has it).

## Markup contract (`data-stats-*`, `stats_page`)

## Funnel scorecard

G8 (`funnel-scorecard`): the event-level log behind the staff screen `/admin/statistik/funnel` (`### Cms`), because `stats_daily` rows are aggregates and cannot give cohorts or weeks. Migration `Version20261107150513`, table `funnel_events` (`id`, `occurred_at`, `event`, `venue_id`, `campaign_code`), mapping-only `Entity\RecordedFunnelEvent`. No personal data by construction.

- **Write: `Shared\Command\RecordFunnelEvent(FunnelEvent $event, ?string $venueId = null, ?string $campaignCode = null)`** is the only way to add a row; `Shared\Funnel\FunnelEvent` is the closed list in funnel order (`preview_opened`, `claim_started`, `claim_verified`, `venue_published`, `inquiry_delivered`, `pro_paid`, `subscription_cancelled`, `brief_sent`). Every module may dispatch it (Shared; Crm may not use Stats). **Inside a command handler dispatch it with `[new DispatchAfterCurrentBusStamp()]`**: the row is then written after your commit and not at all when your command fails (`DispatchAfterCurrentBusMiddleware` drops the queue); from a controller or console command dispatch it plainly. `CommandHandler\RecordFunnelEventHandler` is best effort and **never throws**: it drops (stores as null, and logs the field name only) a venue id that is no UUID or a campaign code that is not a plain `Shared\Funnel\CampaignCode` (`[A-Za-z0-9][A-Za-z0-9_-]{0,39}`, no `@`, no `.`), so the step itself is always recorded; it inserts with DBAL in a savepoint (`Connection::transactional()` nests with savepoints, so a failed insert cannot abort the caller's transaction, and a failed flush cannot close the request's entity manager), and logs `Funnel event {event}: not recorded ({exception_class} at {file}:{line})` when the insert fails, never a value. Only the bus's own transaction around it could still fail. The time is the clock's. Staff-entered campaign codes (G5, G11) should be checked with `CampaignCode::isValid()` where they are typed in; a code never comes from a visitor's request.
- **Table rules.** No foreign key on `venue_id` (a row outlives its venue, as `stats_events.venues`). `chk_funnel_events_event` lists the enum in order and `chk_funnel_events_campaign_code` holds the code pattern; `StatsVocabularyChecksTest` pins the first, so **a new `FunnelEvent` case needs a migration that replaces the CHECK**. Indexes: `(event, occurred_at)`, `(campaign_code)`, `(venue_id, occurred_at)` (the first-touch probe). Tests that count rows must `DELETE FROM funnel_events` first inside their rolled-back transaction; a test that commits (`SubmitInquiryConcurrencyTest`) deletes its own rows.
- **Emitters wired now:** `venue_published` (`Venues\CommandHandler\PublishVenueHandler`: every transition to online, a republish counts again) and `inquiry_delivered` (`Inquiries\CommandHandler\DeliverInquiryHandler`: once per inquiry, right after the venue mail went out). `preview_opened` (`Venues\Controller\VenuePreviewLinkController`, G5: every GET that shows a preview, with the link's campaign; a HEAD, a 404 and a 410 record nothing). Left to their cycles: `claim_started`/`claim_verified` (G6), `pro_paid`/`subscription_cancelled` (G9), `brief_sent` (F13: one brief once, `venueId` null). G6 and G7 must not emit `venue_published` / `inquiry_delivered` again. The scope text's `venue_preview_opened` and `reverse_match_completed` are `preview_opened` and `brief_sent` here.
- **Read: `ReadModel\FunnelScorecardQuery::scorecard(FunnelWindow, FunnelFilter, $now): FunnelScorecard`**, four statements (weeks, totals, per campaign, paying). Weeks are ISO weeks in Europe/Zurich, every week of the window listed (newest first, zeros included); `ValueObject\FunnelWindow` is 4/12/26/52 weeks (`?wochen=`, default 12), `ValueObject\FunnelFilter` is all / without campaign / one code (`?kampagne=`: absent all, `-` without). A venue step counts distinct venues (per week, per campaign or per window), `inquiry_delivered` and `brief_sent` count rows, a venue step without a venue counts each row. **Campaign of an event** = its own code, else the first code ever recorded for that venue if that first touch was at or before the event (a LATERAL probe), else none; so Venues and Inquiries emit without knowing a campaign, and what a venue did before any campaign reached it stays "Ohne Kampagne". `FunnelPaying` is the critical metric of CMO 9.1: venues with a `pro_paid` in the last 365 days and how many of them got an `inquiry_delivered` since their first payment; `withQualifiedInquiry` is null until G7 supplies it (the screen shows "n/a"; that field and `FunnelScorecardQuery::paying()` are the seam).
- **Query ceiling.** Each screen reads one bounded time range of `funnel_events` (at most 52 weeks) three times plus the `pro_paid` rows of 12 months, and outputs at most 52 weeks x 8 steps and one row per campaign. Measured on the dev Postgres with a realistic mix (45 % previews, 36 % inquiries, few payments) spread evenly over 52 weeks and the 52-week window (the worst case, since the default window is 12 weeks): about 0.5 s for the four statements at 30,000 rows, 0.9 s at 100,000, 3 s at 300,000, 12 s at 1,000,000 (the grouped DISTINCT sort and the per-venue probe dominate). Expected volume is tens of thousands of rows a year. **Past about 300,000 rows in the shown window, add a weekly rollup table (like `stats_daily`) instead of reading events.** `FunnelScorecardQueryTest` pins the statement count at 4.
- **Seeds and tests.** `Story\FunnelStory` (loaded by `AppStory`; skips when its two campaigns are already in the log, throws when fewer than 24 venues are published; no event later than now) writes ten weeks, two campaigns and two paying venues over the first 24 demo venues; `Factory\RecordedFunnelEventFactory`. `tests/Unit/Stats/{FunnelWindowTest, FunnelFilterTest}`, `tests/Unit/Shared/CampaignCodeTest`, `tests/Integration/Stats/{RecordFunnelEventHandlerTest, FunnelScorecardQueryTest, FunnelStoryTest}` (incl. the CHECK that refuses an address), `tests/Integration/Cms/FunnelTranslationKeysTest`, `tests/Integration/Venues/PublishVenueFunnelTest`, `tests/Integration/Portal/AcceptSubmissionFunnelTest` (the nested publish: the step follows the outer commit and goes with a rollback), `tests/Application/Inquiries/SubmitInquiryFunnelTest` (the full pipeline, and `funnel_events::text` holds no `@`), `tests/Application/Cms/FunnelControllerTest`; `ModuleBoundariesProbeTest` has clean Crm and Portal fixtures that dispatch the command. `BaselineMigrationTest` now also rolls back and replays every later migration.
- **Not built:** the manual "founder minutes" field (it needs a table, a command and a form; add it with G10 or when the owner asks), a CSV export, conversion rates between steps.
- **Withdraw (G9 finish):** the Shared `Command\WithdrawFunnelEvent(event, venueId, recordedAt)` → `CommandHandler\WithdrawFunnelEventHandler` deletes the one row of that step and venue nearest to `recordedAt` (best effort, never throws). Only a voided payment uses it (`pro_paid`); a term free of charge records no `pro_paid`, so «Zahlende Einträge» counts only paid terms (D18).

## Searches without results (G12 `launch-regions`)

- **Table** `search_misses` (migration `Version20261108101505`, mapping-only `Entity\SearchMiss`): `week_start` (ISO Monday, Europe/Zurich, CHECK), `query` (the URL-encoded canonical `SearchCriteria` query, printable ASCII, 1-2000 characters, CHECK), `searches`, `last_searched_at`; unique `(week_start, query)`. No person: no IP, user agent, session or time of day beyond the last search; `/datenschutz` says so (`legal.privacy.stats.body`, with the 100 characters, the contact-data rule and the 12 months, pinned by `LegalPagesTest`). No `created_at`/`updated_at` (like `funnel_events`).
- **Retention (D44):** `Command\PurgeSearchMisses` (`RETENTION_MONTHS` 12) → `PurgeSearchMissesHandler` (DBAL, `week_start <= now - 12 months + 1 day` as a Zurich date: a row's Monday is its earliest search, and a nightly run is never late) → returns the count; console `app:stats:purge-search-misses` ("N search misses deleted."), step `search-misses-purge` of `bin/cron-daily`. A second run deletes nothing (`PurgeSearchMissesCommandTest`).
- **Write:** `Shared\Command\RecordSearchMiss($query)` → `CommandHandler\RecordSearchMissHandler`: upsert `searches + 1` in a savepoint with DBAL, never throws; an empty, too long or non-ASCII query is dropped and logged without its value. Only Search's listing dispatches it, through `Search\SearchMissFilter` (text cut to 100 characters, no text with contact data; `### Search`).
- **Read:** `ReadModel\SearchMissQuery::weeks(FunnelWindow, $now)` → `list<SearchMissWeek(start, searches, queries, top)>`, newest first, only weeks with a miss, top `TOP` (20) `SearchMissRow(query, parts, searches)`; parts are labelled from `cms` `stats.funnel.misses.param.<key>`, term codes from `venues` `term.<group>.<code>` (`TERM_PARAMS`, pinned to `SearchCriteria::PARAMS` by `SearchMissTest`), `access.<code>`, a town UUID by name (one more statement). `FunnelStory` seeds seven rows.
