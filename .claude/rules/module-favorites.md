### Favorites

Merkliste cookie codec, toggle endpoint, `/merkliste` page.

**Built in #13 (`merkliste`).** No migration, no table: the list lives in the browser. Composer `symfony/security-csrf` (shared with #14).

- **Cookie:** name `merkliste`, host-only, `Path=/`, venue numbers in saved order, comma-separated. On the wire the comma is percent-encoded (`12%2C34%2C56`) on both sides; both readers also accept a raw comma. `Max-Age` 34560000 (400 days, renewed on every write), `SameSite=Lax`, `Secure` on HTTPS, not `HttpOnly` (JS reads it). An empty list deletes it. A trailing comma (`12%2C34%2C`) marks a list written by JS and not yet re-issued: only JS writes it, both readers ignore it, and `POST /merkliste` and `GET /merkliste` drop it.
- **Codec:** `Favorites\ValueObject\MerklisteCookie` (`NAME`, `MAX` = 100, `MAX_AGE_SECONDS`): `fromRequest()`, `parse()`, `isValidNumber()`, `numbers()`, `has()`, `isFull()`, `toggled()`, `without()`, `only()`, `value()`, `toCookie()`. A token matches `^[1-9]\d{0,9}$` and is ≤ 2147483647, so a crafted value cannot reach Postgres out of range; garbage is dropped, duplicates keep their first position, the first 100 win. At 100 an add is refused, nothing is evicted; the codec owns that rule because no server-side list exists (`.claude/rules/validation.md`'s example assumes one). `assets/js/merkliste.js` repeats the rule and the format; change them together.
- **Toggle:** `merkliste_toggle` `POST /merkliste/{number}` (`MerklisteToggleController`), the no-JS path. No command or handler (`.claude/rules/cqrs.md`): nothing is persisted, and a handler cannot set a response cookie. No database either, stale numbers are `/merkliste`'s job. CSRF comes first, through the stateless `SameOriginCsrfTokenManager` (token id `submit`, field `_token`, constant value `csrf-token`, so cached HTML is the same for everyone); a failed check answers 403 and no cookie. This is required: `SameSite=Lax` keeps the cookie off a cross-site POST, but the answer's `Set-Cookie` would still be stored and replace the whole list. Then a 303 to the same-origin `Referer`, else `/merkliste`; a refused add at 100 goes to `/merkliste` with no cookie. `intent=remove` (the exact string, sent by `_remove_button`) only ever removes through `without()`: the same removal twice leaves the entry gone, an absent number sends no `Set-Cookie`, and it is never refused at 100. Without it the route is a true toggle, because the Merken button on a cached page cannot know the state. A number above the INTEGER range is 404. All answers are `private, no-store`, `X-Robots-Tag: noindex, nofollow`.
- **Sync:** `merkliste_sync` `POST /merkliste` (`MerklisteSyncController`) makes the server the last writer, because WebKit caps a cookie written by `document.cookie` at 7 days and leaves one set by a response alone (MK-2). It has no number, so it cannot flip anything, and it echoes the list from the request's `Cookie` header: an empty list writes nothing and never deletes, a clean list writes nothing, anything else is re-issued normalised, which drops the marker. Same CSRF check as the toggle. It answers 204 with no `Location`, so `HttpCache` invalidates no cached page. No database, no session. `merkliste.js` calls it 3 s after the last write of a burst (plain `fetch`, 2 s timeout), 3 s after a page load or bfcache restore that finds the marker, and at once with `keepalive` when the tab is hidden or on `pagehide`. No marker, no request: a visitor with no list or a clean one never sends it, nor does a marked value with no valid entry, and `focus` and `render()` never do. A failure stays silent, the marker stays, and the next page view retries. An answer that leaves the marker (a proxy dropped `Set-Cookie`) is not retried until this tab writes again, so a page cannot loop. Because the server cannot see the browser's cookie, a landing can overwrite a newer write, so each tab keeps a journal of its writes until a sync has landed and, one delay later, nothing of its own is left to send (the cookie is clean, or it carries another tab's marker), or until the page is left (its keepalive carries the list, and whatever runs meanwhile is newer): it re-asserts additions before every sync and at every landing, and removals only at its own landing and only when they came after that flight's snapshot. `MerklisteScriptTest` pins `SYNC_TIMEOUT_MS + 1000 <= SYNC_DELAY_MS`, which that rule needs across tabs.
- **Page:** `merkliste` `GET /merkliste` (`MerklisteController`), the only GET that reads the cookie. Cards come from `ListingQuery::cardsByNumbers()` in saved order through `search/_card.html.twig` with `action: 'remove'`. It prunes: when the normalised list (garbage, duplicates, unpublished or deleted venues gone) differs from what it received, it sends a `Set-Cookie`, so a venue unpublished for a while leaves a list if the page is opened in that window. `private, no-store`, `noindex, nofollow` in the header and the `<meta>`. The empty state, count and full notice are always rendered, `hidden` when not needed, so JS can reveal them.
- **Cached pages never read the cookie:** no `Set-Cookie`, no `Vary: Cookie`, byte-identical HTML. `MerklisteCookieDoesNotVaryTest` pins this with a frozen clock (`mockTime()`), so time-dependent page content cannot flake it.
- **`assets/js/merkliste.js`** loads on every page from `base.html.twig` (one recorded line beside `overlay.js`, because the header count needs it and `{% block scripts %}` is overridden per page). It reads the cookie, sets `aria-pressed` on every `[data-merken]`, fills `[data-merkliste-count]`, and refreshes on bfcache restore, when a tab becomes visible and on `window` `focus` (`visibilitychange` does not fire for two side-by-side windows); on `/merkliste` a refresh reloads when the cookie's list differs from the rendered cards, and it never runs at load, so it cannot loop. One delegated `submit` listener takes over the Merken and remove forms. On `/merkliste` the remove path drops the card in place and moves focus to the next remove button, else the previous one, else the h1. A removal within `REMOVE_GUARD_MS` (450 ms, by `event.timeStamp`, measured from the last performed removal) of the previous one is swallowed, because the next card slides under the pointer and there is no undo; a repeating Enter on a remove button is stopped separately by `event.repeat`, as the OS key repeat can start later than that. Contract: the heart link `[data-merkliste-link]` carries `data-sync-token` (the constant `csrf_token('submit')`, its `href` is the sync URL), `data-count-label` (`__count__`), `data-toast-added`, `data-toast-removed` (`__name__`), `data-toast-full`, `data-toast-link`; a button carries `data-merken` or `data-merkliste-remove` plus `data-merken-name`; the page has `[data-merkliste-total]` (`data-count-one`, `data-count-other`), `[data-merkliste-full]`, `[data-merkliste-empty]`, `[data-merkliste-item]`, `[data-merkliste-title]`. A toast replaces the previous one and goes after 6 s, but stays while it is hovered or focused, so its link cannot vanish under a keyboard user.
- **Templates:** `favorites/_merken_button.html.twig` (parameters unchanged, now with route and `_token`), `favorites/_remove_button.html.twig` (`number`, `name`; the same route with `intent=remove`, so neither a double-click nor a stale tab can re-add), `favorites/merkliste.html.twig`. Styles `assets/styles/favorites/_merken.scss` (the pressed heart fills, so the state is not colour alone), `_merkliste.scss`. Strings in `favorites`.
- **Known limits:** without JS a cached page cannot show the saved state. The button toggles blind and the count stays hidden; `/merkliste` is the no-JS source of truth. MK-2's 400 days on Safari and iOS rest on the re-issue and on WebKit's documentation, not on a test in WebKit; if the re-issue never runs there, a list lasts 7 days from its last change, and 24 hours on a landing page reached through a link-decorated URL from a domain WebKit classifies as a tracker. A removal in one tab during another tab's sync can return (R-D4's bias: a returned entry is one click to fix, a lost one is silent), and, with no time bound, when the first tab's sync got no landing (a failed POST, or a tab the system suspended). One tab: a removal on the next page while the previous page's keepalive is still out returns; that needs a POST slower than about a second.
- **Tests:** `tests/Unit/Favorites/ValueObject/MerklisteCookieTest`, `tests/Unit/Favorites/MerklisteScriptTest` (the constants `merkliste.js` shares with the codec, and its timing), `admin-ui/tests/public/merkliste.test.js` (behaviour of `merkliste.js` on #22's Vitest + jsdom, no config of its own: marker, no-request rule, journal, landed guard, keepalive, removal guard; `location.reload()` and real bfcache stay browser-only), `tests/Application/Favorites/{MerklisteToggleControllerTest, MerklisteSyncControllerTest, MerklistePageTest, MerklisteCookieDoesNotVaryTest}`. Seed the BrowserKit jar with domain `localhost` (`new Cookie('merkliste', $value, null, '/', 'localhost')`), or a response cannot replace or delete it. POSTs send `_token=csrf-token` and `HTTP_SEC_FETCH_SITE: same-origin`.

**Built in #37 (`listing-redesign`).** No migration, no route, no cookie change.

- **Toast markup:** `.icon`, `span.toast__text`, then the optional `.toast__link`. `components/_toast.html.twig` and `toast()` in `merkliste.js` build the same; the script clones the heart link's `.icon`. A toast from the toggle path carries the link for all three messages; the `/merkliste` path has none, the page is already open.
- **`.listing-empty__disc`:** the 72 px disc with a 32 px heart in `/merkliste`'s empty state. The rule is in `search/_listing.scss` with `.listing-empty`, which is what the Merkliste's empty state reuses.
- **Merken pill:** `.merken--card` stands in `.card__top` with its word at every width (`position: relative; z-index: 2; flex: none`), never a disc on the photo; `_merken.scss` has no breakpoint left. `_merken_button` keeps `aria-label` on `variant: 'card'`, byte for byte, and drops it on `'detail'`, so there the word is the button's name: a page that hides it must hide it visually, never with `display: none`.
- **`.merkliste` is written `.listing.merkliste`:** `.listing.container` is two classes, so a single class would lose gap and padding.

**Changed in #41 (`redesign-verification`).** The header heart has no `aria-label`: its name is a `.visually-hidden` word plus the badge, "Merkliste 2", so `merkliste.js` only fills the badge. `data-count-label` and `header.count_label` are gone. axe's `label-content-name-mismatch` flagged the old label on every page with an entry.
