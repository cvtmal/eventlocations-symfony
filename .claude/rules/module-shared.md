**Built in #26 (`cms-pages`).** No migration here (the table is Cms's, see `### Cms`). Shared holds the contracts and the read side, so a public module declares and renders a block without naming Cms; reading `content_blocks` in `Shared\ReadModel` is SQL, not a PHP dependency on Cms (phpat sees no module edge).

- **Contracts** (`Shared\Extension`, autoconfigured): `ContentBlockDefinition` (tag `content_block.definition`; `key()` dotted lower-case and never `landing.…`, `label()`, `placement()`, `maxLength()` in code points of the trimmed text, `fallback(): ?TranslatableInterface`), collected by `ContentBlockRegistry` (`all()` sorted by key, `get()`; a duplicate key throws `\LogicException`). `FooterNoteBlock` (`KEY` `footer.note`, 300, no fallback, strings `shared` `blocks.footer_note.{label,placement}`). `LandingPageSource` (`pages(): list<LandingPageEntry>`, `page(string $keyPrefix): ?LandingPageEntry`) is implemented by Seo. `Shared\ValueObject\LandingPageEntry` (`keyPrefix`, `type`, `name`, `venueCount`, `passesThreshold`, `url` absolute and only above the threshold, `defaultIntro`, `defaultTitle`, `defaultDescription`; `FIELDS` `intro|title|description`, `blockKey($field)` → `landing.canton.zh.title`).
- **Reader:** `Shared\ReadModel\ContentBlocks` (`kernel.reset`) keeps the whole table as one item `snapshot` (`ContentBlocks::ITEM`, locale → key → Markdown) in pool `cache.content_blocks` (`cache.app`, no expiry). `text()`/`html()` fill a cold pool; `peek()`/`peekHtml()` read the pool only and never query; `refresh()` rebuilds it (Cms, after a save's commit); a cache error never fails a page. Every write to the pool is under the transaction-level advisory lock `ContentBlocks::LOCK`, taken before the SELECT: `refresh()` waits for it, a cold read tries it and, when it is taken, serves what it read and stores nothing, so an older snapshot cannot replace a newer one. A cold fill therefore costs a transaction, the try-lock and the SELECT. The item never expires, because a page that only peeks must keep the note and a cached listing may be all that would warm an empty pool; instead the item carries its build time, and `text()` rebuilds a snapshot older than `ContentBlocks::MAX_AGE_SECONDS` (a day, `Psr\Clock\ClockInterface`) while `peek()` keeps serving it, and any other item shape is a miss. That caps what no lock covers: a refresh that failed or died after the commit, a restore, a direct SQL change. The cap is about two days with #19's TTLs (read from them, not run): `text()` runs only on a PHP render and listings stay cached until Zurich midnight, so a snapshot built just after midnight survives another cached day. `make sf c="cache:pool:clear cache.content_blocks"`, then `make sf c="app:http-cache:clear"` (the page store still holds the old text) and a hit on the plain listing apply such a change at once: `cache:clear` leaves this pool alone, because `cache.app` lives in `var/share/<env>/pools/app`. HTML comes from `MarkdownRenderer`, memoized per request; `render()` maps `<h1>` to `<h2>` (the page has its one h1; `MarkdownRenderer` stays as it is for the rest of the back office) and a body with no visible text (a lone link reference, only NBSP) counts as no block. No cross-locale fallback: a locale without a row gives null and the page shows its own catalogue text.
- **Twig** (`Shared\Twig\ContentBlockExtension`, the main request's locale): `content_block(key, fallback = null)` (safe HTML, else the escaped fallback in a `<p>`, else `''`; the fallback is the caller's, else the `ContentBlockDefinition`'s through `ContentBlockRegistry`; may query once on a cold pool), `content_block_peek(key)` (pool only: the footer, error pages), `content_text(key)` (the raw text, else the definition's fallback, for a value that is not Markdown; no template uses it yet). Capture it as `{% set x %}{{ content_block(…) }}{% endset %}`: a plain `{% set x = … %}` loses `is_safe` and `{{ x }}` escapes the HTML, while the captured set is `Markup` (`''` when empty) and survives a `with_context = false` include. Never `|raw`.
- **Footer note:** `templates/shared/_footer_note.html.twig` fills the slot between the canton list and the bottom row with #18's `_footer_links` in `layout/_footer.html.twig` (`.site-footer__note`, `assets/styles/layout/_footer.scss`) through `content_block_peek()` only, so error pages stay query-free (`ErrorPagesQueryFreeTest`, warm and cold). Cold-pool window: while the pool is empty (a fresh `var/share`, `cache:pool:clear`) a page that only peeks lacks the note until a listing or landing hit warms the snapshot; age alone never empties it. A filtered or page-2 listing reads no block, so it warms nothing, and neither does a listing answered from the page store (#19). A page rendered in that window stays in the store without the note for up to its `s-maxage` (a day), until the next purge or clear, so #20 keeps `var/share/<env>/pools` across a deploy or hits a listing before the first public page. A CMS save never leaves the pool cold, and its purge reaches every page, the footer note on detail and legal pages included.
- **Tests:** `tests/Support/Cms/ResetsContentBlocks.php` (`resetContentBlocks()`: the pool is a filesystem pool shared by every test, and a save inside a rolled-back test transaction stores rows that vanish, so call it after the kernel boots and in `tearDown()`), `tests/Support/Cms/HoldsAdvisoryLocks.php` (a second session, because the test's own connection may retake its lock; the test's transaction keeps a lock until the rollback, so take the second session's lock before the first save or refresh), `tests/Support/Cms/RecordingCachePool.php` (`saves`, `onSave`: only record in the callback, because `rebuild()` swallows whatever a save throws, a failed assertion too), `tests/Integration/Shared/ContentBlocksTest.php` (`outsideTheTestTransaction()` runs `rebuild()` on a real BEGIN and COMMIT, the only way to pin that the save comes before the lock's release), `tests/Unit/Shared/Extension/ContentBlockRegistryTest.php`, `tests/Unit/Shared/Twig/ContentBlockExtensionTest.php`.

Built in #19 (`performance-caching`). No migration, no package. This supersedes every `s-maxage=600` line in this file.

- **HttpCache in prod only:** `when@prod` `framework.http_cache` (`trace_level: short`, `X-Symfony-Cache`, `default_ttl: 0`, no client reload or revalidate), with no `public/index.php` change; dev and test stay uncached, so a test wires it by hand (`Tests\Support\Http\ThroughHttpCache`). The short trace reads `miss/store`, then `fresh`. The store is `%kernel.share_dir%/http_cache`, `var/share/<env>/http_cache` under `APP_SHARE_DIR=var/share` (`.env`, Symfony's recipe), so `cache:clear` does not empty it; only `app:http-cache:clear` does. **Nothing but the web user may write the store** (#20: no console run, cron or deploy step as another user leaves a file there). Three failure modes: `var/share/<env>` not writable is a 500 on every URL, `/health` included (`Store`'s constructor cannot create the directory); a store that exists but is not writable answers a new URL `miss/store-failed` and **any URL with a stale entry a 500**, because `Store::lock()` calls `flock()` on a failed `fopen()` (`Store.php:87-88`; fixing it means replacing the `Store`, handed to #20 with its permission check); and the clear race below.
- **`Shared\Http\PublicCache`** holds every lifetime and every new public route uses it: `page()` (a day, `stale-while-revalidate` and `stale-if-error` a day), `listing($now)` (the same, `s-maxage` until the next Zurich midnight, because a listing's order uses the day's seed and page 1 and page 2 must share one), `MISSING_TTL` 3600 (a thrown 404 or 410, through `#[Cache]`, which takes only constants and never overwrites a directive the controller set), `COUNT_BROWSER_TTL` 60, `PLACES_BROWSER_TTL` 3600 (`_search_places`: browser an hour, `s-maxage` `PAGE_TTL`). No browser `max-age` on HTML, so a purge reaches a visitor on the next navigation. `health` is `no-store, private`.
- **`Shared\Http\HttpCacheClearer`** has two ways to discard the store (`invalidate()` makes every entry miss, `clear()` empties it), and never throws (it runs after a committed change; it logs class, file and line, never the message). `invalidate()` is the purge: it renames only the metadata (`md/`) away and removes it, so every URL misses at once, and a request between `Store::lookup()` and the body read still finds its body (bodies in `en/` are content-addressed and never rewritten, so one cannot outlive its metadata as a stale page). A purge therefore frees no disk. `clear(): bool` renames and removes the whole store and any `.purged-*` leftover; it is the only call that frees disk, and a request that looked up a body just before it answers Symfony's raw 500 page (no SEC-1 headers): about 1–3.5×10⁻⁴ per clear per request/s (at 1 request/s, one 500 in about 3,000–9,000 clears) (`docs/performance-baseline.md` §5). The purge path measured 0 in 1,063 clears at 403 request/s. `usage()` walks bytes and files, leftovers included.
- **`app:http-cache:clear [--if-over-limit]`** (`Shared\Console\ClearHttpCacheCommand`) calls `clear()` directly with no bus, because `command.bus`'s `doctrine_transaction` would wake Neon for a file operation, so it runs in the deployed app directory as the web user (#20). A failed clear prints an error and exits 1, because #20's cron sees only the exit code. #20 runs it nightly at 00:05 and after `app:geo:import-towns` and `app:media:regenerate`, and `--if-over-limit` on a 5-minute cron. **The size guard is the only bound on the store:** `Store` never evicts and every filter state, `?q=` value and unknown slug is a new key (an anonymous client measured 20 MiB/s on two local cores). `--if-over-limit` walks the store once and clears it above `HTTP_CACHE_MAX_BYTES` (5 GiB) or `HTTP_CACHE_MAX_FILES` (1,000,000; small pages use up inodes before bytes), both from `.env`; within both limits it prints nothing, because cron mails any output. The store can overshoot a limit by about one cron interval of write rate (measured scaled down: limit plus 0.73 of an interval; at the local worst rate of 25 MiB/s and 5 minutes, about 7.5 GiB over), so production's quota must leave that room. The byte limit counts file bytes, not disk blocks; small entries (404s, counts) take about 6 times their size on disk, and for them the file limit is the bound. The walk takes about 4–9 µs per file (`docs/performance-baseline.md` §9). The guard bounds only the store: anything else can still fill the disk, and a limiter whose pool cannot save its count fails open on a full disk (measured for `phone_reveal`: 25 of 25 allowed against 20; `inquiry_submit` and the admin login share the storage).
- **Accepted windows:** a render in flight during a save can store the old page after the purge, and that URL stays stale until the next `clear()`, so until 00:05 at the latest; this bound depends on #20's nightly cron existing. A clear also removes the `stale-if-error` fallback for every page not rendered since.
- **nginx:** `/assets/` `public, max-age=31536000, immutable`, `/media/` `public, max-age=86400`, never `immutable`, because `app:media:regenerate` rewrites the same URLs. A changed `docker/nginx/` needs `docker compose restart nginx`.
- **Client IP:** HttpCache rewrites `REMOTE_ADDR` and forwards the visitor, so limiters stay per visitor and `isSecure()` holds with no `trusted_proxies` value (`ClientIpBehindHttpCacheTest`). A proxy in front is #20's. A no-JS Merkliste POST invalidates the page in its `Location`, one page and harmless.
- **Accepted trade (D4):** a cached detail page shares one fill-time token, which has no maximum age, so the bot rule weakens to "at least 3 s since that page was rendered".
- **Guard:** `PublicPagesStartNoSessionTest` walks every route outside `/admin`, with every declared method and real parameters, and `PublicCacheHeadersTest` pins the exact `Cache-Control` per route and answer. A new public route needs parameters in the walker (`$parameters`), a row in the table, and, if it is not `public` with an `s-maxage`, `PRIVATE_ROUTES`; only `COOKIE_ROUTES` (`merkliste`, `merkliste_toggle`, `merkliste_sync`) may send a cookie. `Session::isStarted()` proves nothing after the response, because the listener saves and closes the session: check `getUsageIndex()`. Fixtures: `Tests\Support\Http\PublicRouteFixtures`.

The perf stack runs `APP_ENV=prod` too, so `docker/perf/config/trusted-hosts.yaml`, mounted as `config/packages/prod/`, adds `nginx` and `localhost` there and nowhere else; a host's name in a local test or tool stays out, and production's list is never made an env value. `MEDIA_PUBLIC_DIR` is an env variable with `public/media` as its default: production leaves it, and only `bin/prod-import` sets it for its local mirror. `symfony/lock` (`config/packages/lock.yaml`, `flock` in `var/lock`) closes the rate limiter's race. Sentry is `when@prod` only (`config/packages/sentry.yaml`): `send_default_pii: false`, no request bodies, no tracing, `SENTRY_RELEASE` from the `.env.prod.local` each deploy writes. The Datenschutz page names every processor here (`legal.privacy.hosting.*`); a processor dropped in production loses its key and template line.
- **Limiter key:** a limiter keyed on the client IP takes `Shared\Security\ClientIpKey::of($request)` (HMAC-SHA-256 with `kernel.secret`), never the raw IP: `FlockStore` writes the key into a file name it never deletes, and `SlidingWindow` serialises it into the pool. The limit stays per IP, and `RateLimiterKeyTest` pins both places. Login throttling hashes by itself and `admin_totp` keys on a staff UUID (`LimiterLockNamesTest`). Rotating `APP_SECRET` restarts these counters. `bin/cron-daily`'s `lock-sweep` deletes `sf.*.lock` files older than 180 minutes; a limiter window above that needs a longer age there.
- **Cron:** `deploy/crontab.txt`, three lines, absolute paths: `bin/cron-midnight` (00:05, the HTTP cache), `bin/cron-cache-guard` (every 5 minutes offset by 2, only over the store's limits, sharing `bin/cron-lock.sh`'s lock with the midnight clear), `bin/cron-daily` (03:15, one Neon wake-up: inquiry purge, `app:crm:refresh-stages`, `app:crm:renewal-tasks`, `app:crm:purge`, `app:crm:backfill-inquiries`, stuck report, pool prune, staging, session and limiter-lock sweeps). Hostpoint mails a job's output, so a good night prints nothing: `bin/cron-daily` and `bin/cron-midnight` capture a command's output and show it on a failure, because the clear prints a line every time and sends its error to stdout, and the guard prints only when it clears over a limit. A new nightly job is one `step`, `--quiet` if it prints on a good night.
- **Content:** `bin/prod-import` (`export`, `import`, `regenerate [--venue=N]`, `sync`, `purge`, `all`) runs from the owner's Mac: the local php container against Neon with `APP_ENV=prod`, then an additive rsync. Run order: first deploy, `export`, `all`, and only then staff edits. It refuses `--prune` and every other option, and reads `PROD_DATABASE_URL` and `PROD_SSH` from the shell only. Never `make seed` against production.
- **Backups:** `.github/workflows/backup.yaml` (04:17 UTC, `pg_dump -Fc` with a Postgres 18 image and a test restore; repository secrets `NEON_BACKUP_URL`, `SENTRY_CRON_URL`), because the host's `pg_dump` 16 cannot dump Neon 18. The dump goes up as a plain artifact with `retention-days: 7`: the owner decided it needs no encryption. `bin/pull-media-backup` pulls the media to the Mac.
- **Tests and probe:** `tests/Deploy/` (`make release-check`, `make deploy-test`), `tests/Unit/Shared/Doctrine/ChannelBindingMiddlewareTest.php`, `tests/Integration/Shared/Doctrine/ChannelBindingMiddlewareTest.php` (lane and CI Postgres have `ssl=off`, so `channel binding required` proves the setting arrived). `deploy/probe.sh` and `deploy/probe.php` are the one-off account checks; `deploy/` is not in the tarball. The php container is root and a CI runner is not, and Docker Desktop hides that: `bin/build-release`'s `hand_back()` returns the checkout's owner after the container's steps, and `sh tests/Deploy/linux-owner-check.sh` runs the bodies of `ci.yaml`'s `release` and `ops-lint` in a throwaway dind on a real Linux filesystem, checkout owned by uid 1001. That proof is not a GitHub runner, and a change to those jobs must be copied into it. A fake production host in any test is `*.invalid`, never a name that can resolve.
