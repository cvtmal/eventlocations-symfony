# Internationalisation

#2 (`i18n-foundation`) owns `config/packages/translation.yaml` and `src/Shared/Translation/*`; only #2 changes them.

German is the only language for now. French, Italian and English come later and must only add catalogue files and route paths, never rework (S4 in `docs/rpi-cycles.md`).

## Configuration

- `config/packages/translation.yaml`: `default_locale: de`, `enabled_locales: [de]`, translator `fallbacks: [de]`, catalogues in `translations/`.
- The locale comes from the URL only, through the `_locale` default of the matched localized route. `set_locale_from_accept_language` is `false`, so no page varies by `Accept-Language` and pages stay cacheable (S10).
- `set_content_language_from_locale: true` sends `Content-Language: de` with every response.
- `App\Shared\Translation\EnabledLocale` is the single source of truth for served locales in PHP: `all()`, `default()`, `isEnabled()`, `clamp()`. Never read `%kernel.enabled_locales%` elsewhere.

## Catalogues

- Every user-facing string goes through a catalogue (`|trans` in Twig, the translator in PHP). No visible text is written straight into a template or a PHP class.
- One ICU domain per module: `translations/<module>+intl-icu.de.yaml`. The domain is the lower-case module name. Stubs exist for `shared`, `media`, `venues`, `search`, `favorites`, `inquiries` and `seo`; add keys to them, don't create new files for these modules.
- `messages` holds layout strings only and belongs to #1 (`design-system`); `geo` belongs to #3 (`geo-reference-data`). Each of them creates its own file.
- Keys follow `<context>.<description>` inside the domain.
- Swiss German: "ss", never "ß".
- Address: public copy is "du" (E4), mails and `/konto` included, headings too; mails greet "Hallo {name}". `PublicCopyAddressTest` enforces it over every non-staff catalogue and all Twig, PHP and JavaScript, so reword a sentence that starts with a third-person "Sie". Buttons take short imperatives or nouns only ("Suche", "Jetzt starten"). The staff catalogues (`admin`, `cms`, `crm`) stay informal.
- A Symfony message the reader can reach and whose German text says "Sie" (CSRF, upload limit, `Length` defaults) is replaced in `validators+intl-icu.de.yaml`, keyed by its English source text; `FrameworkMessagesTest` reads that source from the framework, add a new one there.
- Pass numbers into messages pre-formatted with `swiss_number`, never through ICU `{n, number}`: the translator locale is `de`, not `de_CH`, so ICU would group with `.` instead of `'`. ICU `plural` and `select` are fine.
- Fixed vocabularies (cantons, taxonomy terms, tiers and badges, rating labels and highlights, FAQ answers) are PHP enums or code-keyed rows; their labels come from catalogues.
  - An enum implements `Symfony\Contracts\Translation\TranslatableInterface`, and `|trans` accepts it directly: `{{ venue.setting|trans }}`.
  - Its key is `<context>.<case value>` in the module's domain, e.g. `setting.lake` in `venues`.
  - Keys built at runtime are invisible to `debug:translation`, so every such enum gets a test that the key of each case exists in `de`.
- Venue-authored text lives in `*_translations` tables (`venue_translations`, `room_translations`, `document_translations`) with a fallback to `de`; see "Content translations". The venue name is a proper noun and stays on `venues`.

## Dates and numbers

- Format through the filters `swiss_number` (`1'234'567.5`, `{{ value|swiss_number(2) }}` for fixed decimals) and `swiss_date` (`05.10.2026`), never `|date` or `number_format`. The © year is the one `|date`, a bare year passed as a string.
- Ranges such as capacities go through the function `swiss_range(min, max)`: `{{ swiss_range(50, 450) }}` renders "50 - 450" (ASCII space-hyphen-space), and equal bounds render one number.
- All three live in `App\Shared\Twig\SwissFormatExtension`, which adds the region `CH` to the current language, so every language keeps Swiss formats.
- Storage and PHP stay UTC; only display is Europe/Zurich.

## Routes

- Every public route is declared in Symfony's localized form from day one: `#[Route(path: ['de' => '/hochzeitslocations'], name: 'listing')]`. German paths are unprefixed. Symfony registers `listing.de` with the `_locale` and `_canonical_route` defaults.
- Templates and PHP call `path('listing')` without a locale suffix; Symfony picks the variant of the current locale.
- Query parameters are stable, language-neutral codes (`?canton=zh&guests=150&setting=lake`), so a URL shared in one language works in another.
- Path segments of landing pages are localized slugs.
- Exempt from the localized form are technical routes only:
  - a route whose name starts with `_` (`_styleguide`, `_profiler*`, `_wdt*`, `_preview_error`);
  - a route whose path starts with `/_` (`/_search/*`);
  - a route that opts out at its declaration with `options: [LocalizedRoutes::UNLOCALIZED => true]` (`App\Shared\Translation\LocalizedRoutes`), as `health` does.
- `tests/Application/Shared/Translation/PublicRoutesAreLocalizedTest.php` enforces this over the app's router: a route not in the localized form fails it, and so does a localized route with no path for one of the enabled locales.

## hreflang

- The Twig function `hreflang_alternates(query = {})` (`App\Shared\Twig\HreflangExtension`, backed by `App\Shared\Translation\HreflangAlternates`) returns one `<locale>-CH` alternate per enabled locale that has a path for the page's route, plus `x-default` pointing at the German URL. URLs are absolute, on the request host.
- The partial `templates/shared/_hreflang.html.twig` renders them as `<link rel="alternate" hreflang="…" href="…">`. Pass `query` for parameters that select a different page, e.g. `{{ include('shared/_hreflang.html.twig', {query: {page: 2}}) }}`.
- It is wired with one line inside the `{% block hreflang %}` that #1 provides in `base.html.twig`: `{{ include('shared/_hreflang.html.twig', ignore_missing = true) }}`.
- Routes not in the localized form (technical routes) get no alternates, and neither does a request that is not safe, such as a POST re-render, which must not advertise its POST URL. Error pages emit none because their templates empty the block, since `_route` is set on a 404 thrown by a matched route. The canonical name is read from `_route`, which the router sets to `listing` for a match of `listing.de`; `_canonical_route` is not kept on the request.

## Content translations

- **Schema**, per translated entity:
  - table `<entity>_translations (id UUID PRIMARY KEY, <entity>_id UUID NOT NULL REFERENCES <entities>(id), locale VARCHAR(2) NOT NULL, …fields, created_at, updated_at)`;
  - `uk_<table>_<entity>_id_locale UNIQUE (<entity>_id, locale)`;
  - `chk_<table>_locale CHECK (locale ~ '^[a-z]{2}$')`, a format check rather than an `IN` list, so a new language needs no migration;
  - an index on the foreign key (`.claude/rules/database.md`).
- **Write side**: validate `locale` with `EnabledLocale::isEnabled()`. Every owner has a `de` row (the importer guarantees it; the owning cycle tests it).
- **Entity side**: a plain per-module entity (`Venues\Entity\VenueTranslation`) with a unidirectional `ManyToOne` to its owner. No shared trait, no mapped superclass.
- **Read side**: read models join the row with `App\Shared\Translation\TranslationJoin`:

  ```php
  $sql = 'SELECT v.id, t.slug, t.summary FROM venues v '
      .$this->translationJoin->localized('venue_translations', 'venue_id', 'v.id', 't')
      .' WHERE v.id = :id';
  $row = $this->connection->fetchAssociative($sql, ['id' => $id] + $this->translationJoin->parameters($locale));
  ```

  `localized()` returns a `LEFT JOIN LATERAL` that picks the row in the requested locale, else the `de` row; `parameters()` binds `:i18n_locale` and `:i18n_fallback_locale`. The fallback is per row, so all fields of a record come from the same language. An owner with no row at all is kept with `NULL` fields. The identifiers are validated because they are interpolated.

## Checks

- `make lint` runs `make lint-translations` (`lint:translations`), which fails on a broken ICU message in any enabled locale.
- `make test` runs, in `tests/Integration/Shared/Translation/`:
  - `TranslationCompletenessTest`: `debug:translation <locale> --only-missing` for every enabled locale, so a key used in `src/` or `templates/` but missing from a catalogue fails;
  - `CatalogueParityTest`: every enabled locale has exactly the keys of `de` in every app domain;
  - `TemplatesHaveNoRawTextTest`: no template under `templates/` shows raw text, letters in `alt`/`title`/`aria-label`/`placeholder`, or a printed string literal without `|trans`. Its `BASELINE` lists the texts of templates written before #2. It only shrinks: an entry that no longer occurs fails the test. `RawTextScannerTest` is the scanner's self-test.
- The scanner does not see text passed as a variable to includes, macros or components, nor strings in PHP. Review checklist item: no user-facing literal in PHP (flash messages, exception text shown to users, form labels without a translation domain).

## Enabling a new language

1. Add the catalogue file for every module domain and for `messages`.
2. Add the locale to `framework.enabled_locales` in `config/packages/translation.yaml`.
3. Add the locale's path to every public route (`'fr' => '/fr/lieux-de-mariage'`); no route is renamed.
4. Add the venue texts as `*_translations` rows; missing rows fall back to `de`.
5. Run `make lint && make test`: the parity, route and completeness tests name what is missing.
